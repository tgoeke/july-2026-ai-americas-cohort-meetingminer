# Adversarial Review Update — ARCHITECTURE-SPINE.md (meetingminer), 2026-08-19 storage/provenance amendment

**Lens:** adversary. Method: construct pairs of units one level down (two stories, two builders, two epics) that each obey every AD to the letter yet build incompatibly. Every surviving pair is a hole to close with a new or tightened AD.

**Scope:** the 2026-08-19 amendment — AD-3 rewritten to two configured roots (`MM_DROPS_ROOT` / `MM_CONTENT_ROOT`) with an *arrived vs produced* anchor rule; new AD-17 (a Postgres row per evidence file: path, root, `sha256`, `byte_size`, stage); AD-9 extended to permit inference on an on-prem LAN host with no mandatory local fallback; the companion `specs/spec-meetingminer/storage-layout.md`. Prior closures from `review-adversarial.md` (2026-08-17) and `review-adversarial-update-2026-08-18.md` were re-checked and hold except where named below.

**Evidence base:** the amended spine and `storage-layout.md`; the next two units to be built (`spec-2-1a-evidence-paths-anchored-to-configured-roots.md`, `spec-2-1b-bring-your-own-recording-drops.md`); the real tree — migrations `0001`–`0007`, `pipeline/stages/transcribe.py`, `pipeline/stages/align.py`, `pipeline/outputs.py`, `projections/publish_gate.py`, `config.py`, `config.yaml`, `adapters/{ocr,stt,embed}/`, and `api/media.py` as it exists on branch `story/2-1`; `epics.md` stories 4.3–4.5 and 5.2–5.4; `sprint-status.yaml`.

**Verdict: THE AMENDMENT IS DIRECTIONALLY RIGHT AND LEAKS AT THREE SEAMS IT OPENED ITSELF.** Naming two roots and demanding a row per file are both correct calls, and several old attacks now fail cleanly. But the amendment (a) reuses an existing column name, `drop_relative_path`, for a *different* anchor than the column already carries in shipped code, (b) declares "exactly two roots" while three shipped/planned documents place a third writable location — the publish folder — inside, beside, or outside them, into a namespace the media route serves ungated by path, and (c) names `transcript_source` as AD-17's reference row shape when that row has no `stage` column, no room for a second consumer of one file, and conflates a produced file's provenance with a derivation's output. AD-9's fallback silence is a real fork between the demo path and the eval path, made worse by three incompatible fallback precedents already sitting in `config.yaml`. Twelve findings: 2 critical, 4 high, 5 medium, 1 low.

## CRITICAL

### C1. `drop_relative_path` already means "relative to the drop directory"; AD-3 and AD-17 now mean "relative to the drops root" — same name, two anchors, one codebase

- **Units:** story **2.1a** (`meeting_media.drop_relative_path`, new migration `0009`) vs the shipped **1.5 transcript lane** (`transcript_source.drop_relative_path`, migration `0005`, written by `pipeline/stages/align.py`). Story **1.12/1.13 augmentation** is the collateral.
- **The clash.** AD-3 as amended: arrived material "is recorded as `<drop-dir>/<filename>` against the drops root." AD-17 repeats it: "the path relative to its **root**." `storage-layout.md` §4 repeats it again. But the column that AD-17 explicitly nominates as the shape to copy — "`transcript_source` (migration `0005`) is the reference row shape and is matched rather than re-invented" — stores something else. `migrations/0005_transcripts_participants.sql:29` documents it as "Path inside the source drop, **relative to the drop directory**", and `align.py:201` writes `"drop_relative_path": path.name` — a bare filename. Resolution goes through `job.drop_path`.
  - *Build A (2.1a builder, obeying AD-3's sentence):* `meeting_media.drop_relative_path = "2026-05-14-orders-demo-a1b2c3d4/recording.mp4"`, resolved as `MM_DROPS_ROOT / value`. This is what 2.1a's own acceptance criterion asks for ("the database stores its path relative to that root").
  - *Build B (any later builder, obeying AD-17's "match rather than re-invent"):* `drop_relative_path = "recording.mp4"`, resolved as `resolve(job.drop_relative_path) / value` — exactly like the transcript row beside it.
  - Both are AD-cited, both are named identically, and both live in the same schema. A single generic resolver written against either one silently produces `MM_DROPS_ROOT/recording.mp4` or `MM_DROPS_ROOT/<dir>/<dir>/recording.mp4`. Neither errors at write time; both fail at read time, in the media route, for one class of file only.
- **The second-order failure is worse, and it is the augmentation path.** After an AD-14 augmenting re-arm, `job.drop_relative_path` points at the `-002` sibling. A *drop-dir-relative* row therefore silently re-targets the new drop; a *root-relative* row keeps pointing at the original. For transcripts that is invisible (AD-1 requires the augmenting drop to carry every transcript the occurrence already had). For the recording it is a live divergence: after story 1.12's late-recording augmentation, Build A serves the recording out of drop `-001` — the one whose `sha256` was recorded — while Build B serves it out of `-002`, whose bytes AD-1 never required to be identical (the recovered file legitimately comes from the recorder's personal drive and "the two ids may differ"). Replay, the checksum check, and any future eval-time byte assertion disagree about which file *is* the meeting's recording.
- **Why it survives review:** the two columns are never joined, and each build's tests pass against its own fixture. The disagreement is only observable after a re-emit, which is the one path nobody exercises before demo week.
- **Minimal tightening (AD-17, one clause + a migration note):** state the anchor granularity explicitly — *a stored path is relative to its configured root, never to a directory named by another row* — and require migration `0009` to bring `transcript_source.drop_relative_path` to root-relative in the same change (or rename the new column `drop_root_path` and leave `0005` alone, documenting both). Do not ship two live spellings. Also delete or qualify AD-17's "matched rather than re-invented," which currently instructs builders to copy the wrong anchor.

### C2. "Exactly two roots" vs the publish folder — a third writable location that AD-3 forbids recording, storage-layout puts inside the content root, and the media route serves ungated

- **Units:** story **4.3** (per-moment approval & publishing: "exported to the publish folder, and ADRs additionally committed to the plain local git repository") and story **4.5** (digest example email file) vs story **2.1/2.1a** (`api/media.py`, root anchoring) vs the spine's own **Recovery** convention.
- **The clash.** Three statements in the amended material disagree about where published bytes live:
  1. AD-3: "There are **two** configured, permanent storage roots … every recorded path is relative to exactly one of them."
  2. `storage-layout.md` §1: the content root holds "frames, screenshots, extracted audio, **published artifacts**."
  3. The spine's own component and deployment diagrams, and the Recovery convention: `publish folder + local git` is a **third** filesystem box, backed up separately ("back up a `pg_dump` and the publish folder alongside the drops directory"), and AD-3's own rule text lists only "frames, screenshots, extracted audio" for the content root.
  - *Build A (4.3 builder reading `storage-layout.md` §1):* exports land at `<content-root>/publish/…`, with a git repo inside the content root. Consequence, verified in code: `api/media.py`'s path-addressed route `GET /media/{path:path}` streams **any** file under the content root by client-supplied relative path, with a containment/symlink guard and **no database row lookup and no state check**. Every exported ADR — and every `.git` object under it — becomes byte-servable to any client that can guess a path, while AD-4's publish gate governs *projections* only. The one gate the architecture has for artifact visibility does not sit on the byte route.
  - *Build B (4.3 builder reading AD-3 + the diagrams):* a third configured root, `MM_PUBLISH_ROOT`. Now a published artifact's file path is recordable against no root AD-3 admits, so either the artifact row stores an absolute path (AD-3 violation) or it stores a path with no anchor (AD-17 violation), and the AD-17 provenance row for an exported file has nowhere to point.
  - Both builds cite the amendment. They differ on backup scope, on `rebuild`'s blast radius, and on whether approved-but-unpublished neighbours are reachable over HTTP.
- **Why it survives review:** Epic 4 is four epics away from the amendment; by then `storage-layout.md` §1's one word ("published artifacts") reads as settled, and the media route is a shipped, reviewed file nobody re-opens.
- **Minimal tightening (AD-3 + AD-17, two sentences):** (1) Name the publish folder as what it is — a third configured location, `MM_PUBLISH_ROOT`, **outside** both evidence roots, holding human-facing output rather than evidence; correct `storage-layout.md` §1, which currently contradicts AD-3's own rule text. (2) State that the content root is a **byte-servable namespace**: nothing may be written there that is not intended to be streamable by path, and any file class that needs a gate is served id-addressed through a route that reads its row. (3) Add to AD-17 the enforcement half it is missing: *a path-addressed byte route must resolve through a row, or the namespace it serves must contain only row-backed evidence.* Today it requires the row to exist and never requires anyone to consult it.

## HIGH

### H1. AD-17 mandates a `stage` column its own reference row does not have, and never says whether provenance is per-table columns or one registry

- **Units:** any two of story **2.1a** (`meeting_media`), a future **frames/screenshots conformance** story, and story **5.2** (a run report that wants to verify evidence files).
- **The clash.** AD-17 requires each row to carry "the path…, which root…, its `sha256`, its `byte_size`, and **the stage that wrote or read it**", then names `transcript_source` as the shape to match. `transcript_source` has no stage column: its columns are `kind`, `format`, `drop_relative_path`, `content_path`, `sha256`, `byte_size`, `segment_count`, `engine`, `model`, `language`, `segments`. `storage-layout.md` §5 reproduces the same contradiction — mandatory row of five things, then "`transcript_source` is the reference implementation of this row shape."
  - *Build A:* matches the reference literally — new tables get path + root + `sha256` + `byte_size`, no stage. AD-cited.
  - *Build B:* obeys the sentence — adds `stage text NOT NULL`, and (following `job_stage`'s precedent) constrains it to the eight pipeline stage names. AD-cited. Then Epic 4's publish export needs a row and there is no stage that wrote it: `publish` is an API action, not a pipeline stage, so the CHECK constraint refuses the row or the enum quietly grows a non-stage value.
  - *The same fork on location:* "matched rather than re-invented" describes a *row shape*, not a *place*. Build C creates one `evidence_file` registry (path, root, sha256, byte_size, stage, owner table+id) and rows every file through it; Build D adds columns per entity table, which is what 2.1a actually does. Both satisfy AD-17. A backup verifier, a `rebuild --verify`, or eval check 5.2 then cannot enumerate "all evidence files" without per-table knowledge that only one of the two builds provides.
  - **Already ambiguous, in shipped code:** `transcribe.py` extracts `audio/audio.wav` (line 163) *and* hands it to the diarizer (line 185). Two consumers, one file, one "the stage that wrote or read it".
- **Minimal tightening (AD-17):** pin three things in one paragraph — (a) the row lives with the entity it describes (per-table columns), and a single read-only SQL view enumerates all of them for verifiers; (b) the provenance field is *the stage or API action that produced the file*, one value, set by the writer and never by a reader; (c) `transcript_source` is the reference for the *path/checksum/size triple* only, and migration `0009` brings it up to the full shape rather than being cited as already compliant.

### H2. AD-17 makes substitution detectable and never says what detection means — and the right answer is opposite for the two roots

- **Units:** story **2.1a** (`probe` records and re-checks the recording's `sha256`) vs the shipped **`align` stage** (re-parses the provided transcript from the drop on every run, with `sha256` already recorded) vs a future **frames** conformance story.
- **The clash.** AD-17's stated purpose is "a substituted file being undetectable." It stops there. 2.1a's own I/O matrix resolves it one way — *"Stage rerun, changed file → New checksum recorded and the change logged — visible, not silent"* — i.e. a mutated write-once drop is **accepted**, and the row is updated to describe the new bytes.
  - *Build A (2.1a as specified):* accept and re-record. The recording that a published citation was minted against is replaceable with no failure anywhere; the row that was supposed to prove the input did not change is the thing that gets rewritten.
  - *Build B (`align` builder, reading AD-1 "write-once" and AD-13 "read-only after intake"):* a checksum mismatch on drop material is a violated invariant → `StageError`, job fails, the operator is told the drop was tampered with. Equally AD-cited, and arguably the only reading under which AD-17's "Prevents" clause means anything.
  - Same drop, same rerun, two stages, opposite outcomes: `probe` records the new hash and continues; `align` fails the job. Whichever runs first decides.
  - **And the correct policy genuinely differs by anchor**, which no AD says: arrived files are immutable by AD-1/AD-13, so a mismatch is corruption. Produced files are re-derived by AD-11 reruns and **are not bit-reproducible** — ffmpeg JPEG output varies across builds and flags — so a mismatch is normal. A builder applying one policy to both either fails every legitimate `frames` rerun or accepts every tampered drop.
- **Minimal tightening (AD-17 + a clause in AD-11):** state the two policies explicitly. *Drops-root anchored: a checksum mismatch is a stage failure, never a silent re-record — the drop is write-once. Content-root anchored: the checksum describes the current output and is rewritten by the rerun that produced it; it is corroboration for serving and backup, not a tamper signal.* Then fix 2.1a's matrix row, which currently specifies the drops-root case the wrong way round.

### H3. AD-9 permits a LAN inference host and mandates no fallback; `config.yaml` already carries three incompatible fallback precedents and no slot for an STT endpoint

- **Units:** a **demo-path** builder (a `transcribe` retune binding the `Stt` port to VM 120 `cuda-asr`, the host AD-9's Structural Seed names) vs an **eval-path** builder (story **5.2** deterministic capture checks, story **5.4** judge/engine bake-off).
- **The clash.** AD-9 now says an engine "may run in-process, as a host process, on an **on-prem LAN host** reached over HTTP, or behind a provider API — which one is a `config.yaml` binding (`providers.<name>.base_url`, AD-10)", and the Structural Seed adds that VM 120 "is available infrastructure rather than a best-effort dependency, and **no rule here requires a local fallback** for a stage that names it." What happens when it is unreachable is left open, and the repo supplies three mutually incompatible answers to copy:
  - `ocr.fallback: tesseract` — engaged **at construction time**, when the primary "is unavailable on this host" (`adapters/ocr/__init__.py`), i.e. a host-capability probe, not a per-call network condition.
  - `llm.roles.*.fallback: ollama/qwen3:32b` — a second model id per role, AD-10's documented default.
  - `embedder` — "deliberately **no fallback key**" (`adapters/embed/__init__.py`), raising `EmbedderUnavailableError` when the host is unreachable (`adapters/embed/port.py:63`).
  - *Build A (demo path):* adds `stt.fallback: mlx-whisper`, copying the OCR shape. Because the OCR shape probes *availability at construction*, an intermittently reachable LAN host is judged available at stage start and then fails mid-transcription, or is judged unavailable once and silently downgrades the whole run to a different acoustic model.
  - *Build B (eval path):* copies the embedder shape — no fallback, hard error, job fails, operator restarts VM 120. Deterministic, and it makes the demo unrunnable whenever VM 116 has the GPU (the Structural Seed notes the two VMs share it and must not run at once).
  - **Both builds break something the spine asserts elsewhere.** AD-11: "Every stage is idempotent — rerunning it **deterministically** overwrites its own outputs." A fallback that engages on reachability makes the same job produce parakeet segments today and whisper segments tomorrow, with different `stt_start_ms` and `alignment_delta_ms` values, into the `stt_start_ms` / `alignment_delta_ms` columns AD-13 makes the anchor for moment identity. AD-10: the eval harness "snapshots the full **resolved** config into each run's metadata" — under an engaged fallback the snapshot names the engine that was *configured*, not the one that ran, so two runs with identical metadata are not comparable. AD-8's rerun trigger fires only for the embedder, so an STT engine substitution triggers no eval rerun rule at all.
  - **Separately, the binding AD-9 describes has no config slot.** `stt:` carries `engine` and `model` only; `providers:` carries `anthropic`, `openai`, `openrouter`, `ollama`. There is no `providers.cuda-asr`, and `parakeet-mlx` is a *local MLX* engine, not an HTTP client for the NeMo service AD-9 names. Two builders will invent the shape differently (`stt.base_url` vs `stt.provider: cuda-asr` + a new `providers` entry vs a new `engine: parakeet-http`), and the eval config snapshot's schema forks with it.
- **Minimal tightening (AD-9 + AD-10):** (1) Say what unreachable means, once, for every port: *a configured engine that cannot be reached fails the stage with a named error; a fallback engages only when it is declared in `config.yaml`, and when it engages the substitution is recorded on the row it produced and on the job.* (2) Require the *effective* engine/model — not only the configured one — in the eval run snapshot, and extend AD-8's rerun trigger from the embedder to any port whose effective binding changed between runs. (3) Add the endpoint-bearing STT binding shape to AD-10's config contract before a builder invents it, since AD-9 now points at a host the config file cannot address.

### H4. Two drop producers, two different answers to "this source arrived again" — and the bring-your-own path has no augmentation route and no transcript-only identity

- **Units:** story **2.1b** (bring-your-own-recording drop tool) vs the shipped **puller `--re-emit`** behaviour (story 1.13) and the AD-14 augmentation door.
- **The clash.** AD-1 states the re-emit rule as a *puller* behaviour: "The puller emits augmenting drops only under its opt-in `--re-emit` flag … writes a *new sibling* drop at `-002`, `-003` … carrying `schemaVersion: 2` and `augments` — but only when the pass would bring the newest existing drop something it lacks." Nothing states it as an obligation on *drop producers in general*. 2.1b is a second drop producer and its matrix answers the same situation differently: *"Re-run on the same file → Drop for that content hash already finalized → Reported as existing; nothing rewritten."*
  - *Build A (2.1b as specified):* a user who ingests a local video, then later obtains its transcript (or a participant list), re-runs the tool and is told `exists`. There is no path by which a hand-brought meeting ever gains a transcript — the exact capability AD-1's version-2 `augments` field was added to provide, and which 2.1b's own Design Notes claim it has ("a hand-brought video is augmentable later by exactly the same mechanism as a pulled one"). It is not: the mechanism lives in `emit-drop.js --re-emit`, which 2.1b reuses for naming and finalize but not for the re-emit decision.
  - *Build B (a builder taking the Design Notes seriously):* implements `-002` sibling emission in the BYO tool with its own "brings something new" test. Now two producers each own a copy of the intake door's comparison logic (AD-1: "the same test intake applies, so the puller never finalizes a write-once drop the door will refuse"), and they drift — the puller compares against `<stem> org chart.json` availability, the BYO tool against whatever a local file offers.
  - **And the identity rule has a hole 2.1b's own matrix walks into.** `sourceId` is "derived from the video's own content — its `sha256`". Row 3 of the same matrix is *"Transcript only → A local transcript file, no video → Valid transcript-only drop."* That drop needs a `sourceId` and there is no video to hash. AD-1 defines `sourceId` only as "the occurrence's stable identity **the puller already holds**." The builder invents one — path hash, transcript hash, a UUID — and a UUID or path-derived id re-mints a second occurrence on the next run, which is precisely what AD-14's `UNIQUE(source_id)` and the live-job index exist to prevent. Two BYO invocations, one meeting, or one file, two meetings, depending on an unstated choice.
- **Minimal tightening (AD-1):** restate the re-emit and identity rules as **producer obligations**, not puller behaviour: *any drop producer that re-encounters an already-finalized occurrence emits an augmenting sibling when and only when it brings evidence the newest existing drop lacks, applying the same test the intake door applies; producers without a native occurrence identity derive `sourceId` from the content hash of the drop's primary evidence file — the recording when one exists, else the transcript — so the same input always resolves to the same occurrence.* Extract the comparison into one place both producers call rather than two implementations of one rule.

## MEDIUM

### M1. "Produced" material has exactly one legal layout, and three planned files do not fit it

- **Units:** story **4.5** (digest example email file) vs story **2.1a** (backfill report) vs the `rebuild` CLI (AD-4) vs the content-root guard.
- **The clash.** AD-3: produced material "is written as `meetings/<meeting_id>/<subdir>/<filename>` against the content root." `pipeline/outputs.py:assert_private_meeting_subdir` enforces exactly that shape and refuses anything else. But several produced files are not meeting-scoped: 4.5's "single example email file summarizing meetings", a `rebuild` report, 2.1a's backfill output. A builder either invents `<content-root>/digests/…` (outside the guard, and — per C2 — instantly byte-servable), writes into the publish folder (which AD-3 does not admit), or writes into the repo. All three are defensible; none is stated.
- **Minimal tightening (AD-3):** either name a non-meeting subtree under the content root and extend the guard to it, or state that corpus-level produced output is not evidence, does not live under either root, and carries no AD-17 row.

### M2. Eval run artifacts: AD-17's "every file" and AD-16's "never writes server tables" cannot both hold if run artifacts are in scope

- **Units:** story **5.2** (immutable `evals/runs/<run-id>/` folder) vs story **5.3/5.5** (checks that surface evidence for human judging) vs AD-17.
- **The clash.** AD-17 binds "every file the system stores or serves." Eval run folders live in the repo, under neither root, with no rows — and AD-16 forbids the harness from writing server tables at all, so it *cannot* create AD-17 rows even if they were required. A 5.2 builder reads AD-16 as an exemption; a 5.3 builder writing check 2.4's "sequential-capture OCR similarity > 0.9 pairs … listed for human judging" naturally copies the screenshot pairs into the run folder, producing unrowed, unchecksummed copies of evidence in a third location that no backup rule covers and no `rebuild` reconstructs.
- **Minimal tightening (AD-17):** scope it in its own first sentence — *every **evidence** file under either configured root, written or read by a server component*. Then add one line to AD-16: run artifacts reference evidence by id, never by copied bytes.

### M3. The two-root split has no representation on the wire, and one route already resolves client-supplied paths

- **Units:** story **2.2/2.3** (moment view, screenshot series — anything that wants to hand back a transcript or a drop-anchored asset) vs the shipped `api/media.py`.
- **The clash.** AD-17 requires the row to record *which root*. Nothing carries that discriminator outside the database. `GET /media/{path:path}` resolves against `MM_CONTENT_ROOT` only, by client-supplied relative path. The moment 2.1a makes the recording id-addressed and row-resolved while frames/screenshots stay path-addressed and unresolved, there are two addressing schemes for one evidence bundle; a builder wanting a transcript download either adds `/media/drops/{path}` (client-supplied path now selects a root) or extends the existing route to try both roots (containment guard now has two answers).
- **Minimal tightening (a convention row):** *drop-anchored material is served id-addressed only, resolved through its row; the path-addressed media route resolves against the content root and no other.* One sentence, and it also closes half of C2.

### M4. `transcript_source` is simultaneously the audio file's provenance row and the STT lane's output row, and `UNIQUE(meeting_id, kind)` allows only one

- **Units:** story **5.4** (LLM/engine bake-off: run N engines over one input and compare) vs the shipped **`transcribe` stage** vs a future **diarizer** story.
- **The clash.** For `kind='stt'` the row's `content_path`, `sha256` and `byte_size` describe the extracted `audio/audio.wav` (`transcribe.py:189-197`), while `segments`, `engine`, `model` describe the STT derivation. `UNIQUE (meeting_id, kind)` permits exactly one. A second engine over the same audio therefore overwrites the first row — including the audio's own provenance — or the second engine's output lives somewhere with no file row at all. The diarizer already reads the same WAV, so AD-17's single "stage that wrote or read it" is two-valued today.
- **Minimal tightening (AD-17 + a migration note):** separate the **file row** (one per stored file, one writer, N readers) from the **derivation row** (one per engine run over that file, referencing it). This is the same split H1 asks for and makes the bake-off representable without a schema fight in Epic 5.

### M5. "Arrived" is defined by how the file came to exist, and the bring-your-own tool *produces* the file it calls arrived

- **Units:** story **2.1b** vs AD-3's rule text.
- **The clash.** AD-3: "Which one is a property of how the file came to exist… Material that **arrived** (the recording, provided transcripts, `metadata.json`) stays in its write-once drop… Material **this pipeline produced** (frames, screenshots, extracted audio) is written… against the content root." The BYO tool writes a byte-identical copy of a user's local file into the drops root: from the system's point of view the file was *created by a tool in this repo*, not by an external source. `storage-layout.md` §6 settles it correctly; the spine sentence alone does not, and the spine is what a builder reads first. A builder reasoning strictly from AD-3 puts the copy under the content root and finalizes a drop with no `recording.mp4` — schema-valid if a transcript is present, and the meeting ingests transcript-only with a stranded video.
- **Minimal tightening (AD-3, one clause):** define the classes mechanically rather than by origin story — *arrived = written by a drop producer before intake, anchored to the drops root; produced = written by a pipeline stage after intake, anchored to the content root.* No judgement call remains.

## LOW

### L1. Non-schema files inside a drop are now stored in permanent, backed-up space with no rows and no owner

AD-1 says files not named by the schema "are ignored at intake" (the puller's generated summaries, a copied `_source.json`). AD-3 now makes the drops root permanent backed-up storage, and AD-17 binds "every file the system **stores**". A verifier built from AD-17 reports them as orphans; intake built from AD-1 ignores them; a backup sizing estimate counts them. Harmless, but say once whether "stores" means "wrote" or "keeps on a managed root."

## Attacks that failed (the amendment holds)

- **AD-3 vs AD-1 write-once.** No contradiction: the drops root's permanence is stated in the rule itself, the three post-ingest readers are enumerated, and the Recovery convention already requires both roots to be backed up together. The "clearable landing zone" misreading is explicitly blocked, including as a Block-If in 2.1a.
- **AD-3 vs AD-13 read-only drop contents.** Consistent. Nothing in the amended text authorizes a write inside a drop, and `storage-layout.md` §2 says so directly.
- **AD-3 vs AD-11 idempotent reruns.** Consistent, and already implemented: `pipeline/outputs.py` gives the content root a stage-then-replace protocol with backup restore, so a failed rerun leaves both files and rows intact.
- **AD-3's meeting-id keying vs AD-14's re-arm.** Holds as claimed — produced material keyed by `meeting_id` genuinely survives a re-emit that changes the drop directory, because AD-14 keeps the meeting id.
- **AD-4 single-writer vs AD-17.** No seam: AD-17 adds rows in Postgres, which the projections module only reads.
- **AD-2 two-owners attack on `meeting_media`.** No seam: `meeting_media` is worker-written and API-read; 2.1a keeps that split.
