- (capability) CAP-1: system status surface in the UI showing health of dependencies the product needs (LLM role bindings/keys, stores, api, worker) — degraded state visible without running a feature into the failure
- (capability) CAP-2: conditions requiring user action are stated as actions in the UI (what is broken, what the user must do, e.g. set key in .env + restart) — not just red indicators
- (capability) CAP-3: feature-path failures name the failing dependency and point at the status surface (consistent with chat-fallback-timeout CAP-4)
- (constraint) Secrets never serialize — status may state a key is missing/invalid, never echo any part of its value (aligned with ui-reimagine allowlist rule)
- (constraint) Status is read-only; remediation stays the file contract (.env/config.yaml edit + restart) and the UI states that path
- (constraint) Health checks must be free: no paid LLM completion as a probe; key validity via free endpoints (e.g. provider model list) or recorded last-failure state
- (constraint) No silent fallback anywhere (owner direction of record); a degraded dependency reads as degraded, never auto-substituted
- (assumption) Assumed scope is the existing web UI (persistent chrome + a status view), sized to fit the initial implementation, not a new ops product
- (question) Placement: persistent banner/indicator in chrome that expands, a dedicated status page, or both?
- (question) Does v1 status include worker/job-backlog state, or only the interactive path (api, stores, chat/search bindings)?
- (question) Check cadence: on page load only, or periodic polling while the app is open?
