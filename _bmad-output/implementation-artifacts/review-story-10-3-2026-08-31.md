### F1 — An explicit first ordinal leaves the sequence poised to reuse it

- **Location:** `server/meetingminer/migrations/0017_thread_color_ordinal.sql:63-70`
- **Severity:** High
- **Finding:** The reserve trigger compares an explicit ordinal only with `last_value`. On a fresh sequence, `last_value` is `1` while `is_called` is false, so explicitly importing ordinal `1` does not call `setval`. The next default allocation returns `1` again and fails the unique constraint. This violates the frozen matrix row that accepts an explicit import ordinal and requires later allocation to advance past it.
- **Evidence:** Against an empty private database immediately after migration 0017, `thread_color_ordinal_seq` reported `last_value=1, is_called=false`. Inserting a thread with `color_ordinal=1` succeeded; the next insert omitting the ordinal failed with `UniqueViolation: Key (color_ordinal)=(1) already exists.`
- **Suggested direction:** Make reservation account for both `last_value` and `is_called`, so an explicit value equal to the uncalled sequence start marks that value as consumed before any default insert can receive it. Preserve the ordinary `derive_threads` path: it omits the ordinal and must continue to allocate from the sequence without caller changes.

Status: resolved red-first. The added regression failed on the unfixed migration with the duplicate-key error above. After the reservation comparison was corrected, the regression plus the original ordinal/list suite passed: 15 passed.

### F2 — The two mandated anchors make level transitions disagree at boundaries

- **Location:** `server/meetingminer/api/threads.py:26-33,154-175,205-235`
- **Severity:** High
- **Finding:** Coarse selection and all envelope totals use `topic_mention.anchor_ms`, while the fine rows use and filter on `moment.start_ms`. The two values can straddle any client-supplied window or bucket boundary. A response can therefore report `momentCount: 1` and return no moments, or return a moment while reporting zero mentions/moments. The module's assertion that anchors coincide for every bucket wider than a moment is false whenever a bucket boundary falls between them.
- **Evidence:** For a moment starting at 59 seconds whose mention anchor is 61 seconds, a `[60s,62s]` window includes the mention in `_WINDOW_TOTALS` and the coarse tiers but excludes the row in `_MOMENTS_LEVEL`; `[58s,60s]` produces the inverse. Increasing bucket width does not remove the boundary—placing the same pair around any ladder boundary reproduces the disagreement. The frozen contract simultaneously requires coarse levels to use `anchor_ms`, fine `occurredAt` to derive from `startMs`, and counts to agree across levels.
- **Suggested direction:** Amend the frozen contract to choose one canonical semantic anchor for window membership and level transitions, then re-derive the query and wire requirements from that choice. If fine rows remain moment-anchored, coarse aggregation needs an equivalent moment start without violating the no-`moment` constraint; if mention anchors own membership, the contract must define how a returned moment whose `occurredAt` precedes the requested window is represented. Do not hide the inconsistency by changing only the envelope count.

Status: open; rooted in contradictory frozen-spec requirements and requires an owner decision before remediation.

### F5 — OpenAPI makes the union discriminator optional in every tier

- **Location:** `server/meetingminer/api/threads.py:410-439`
- **Severity:** Medium
- **Finding:** Each response model gives `level` a default value. Pydantic therefore omits `level` from that schema's `required` list even though the top-level `oneOf` declares it as the discriminator. Runtime responses currently include the field, but generated clients can type it as optional and cannot rely on it to narrow the four exact tiers.
- **Evidence:** The generated OpenAPI response correctly contains a four-entry `oneOf` and discriminator mapping, but the `required` arrays for `BandsTimeline`, `MeetingsTimeline`, `MomentsTimeline`, and `EvidenceTimeline` all omit `level`. This is the generated-contract path explicitly called out for review; the existing whole-key runtime test cannot detect it.
- **Suggested direction:** Make each tier's literal `level` field required and pass it explicitly at construction sites. Retain a hard startup check that the four required literals exactly match the domain `LEVELS` vocabulary, and add an OpenAPI regression asserting both the discriminator mapping and required field.

Status: resolved red-first. The OpenAPI regression failed against the unfixed schemas because `level` was absent from every tier's `required` list. After making the discriminator explicit at construction, the regression plus both original story suites passed: 51 passed.

### F4 — Exact ladder boundaries are counted as an extra bucket

- **Location:** `server/meetingminer/domain/thread_timeline.py:121-146`
- **Severity:** Medium
- **Finding:** `plan_buckets` adds one millisecond to every inclusive window before taking the ceiling. Because the final bucket is already defined as closed on the window end, an interval that is exactly `TARGET_BUCKETS` ladder steps long needs exactly `TARGET_BUCKETS` buckets, not one more. The extra millisecond forces the planner to jump to the next ladder step at every exact boundary.
- **Evidence:** A window of `1:59:59.999` returns `(60000, 120)`, but extending it by one millisecond to exactly two hours returns `(300000, 25)`. The two-hour band loses fivefold resolution even though 120 closed-final one-minute buckets cover it exactly.
- **Suggested direction:** Compute the positive span with a ceiling at millisecond precision and a minimum of one, without adding a millisecond to an already integral duration. Pin zero-length, sub-millisecond, exact-boundary, and one-millisecond-over-boundary behavior.

Status: resolved red-first. The added exact-boundary regression failed with `(300000, 25)` against the unfixed planner. After switching to integer-microsecond ceiling without the extra millisecond, the regression plus the original timeline suite passed: 36 passed.

### F3 — The record does not enforce strict ordinal non-reuse after deletion

- **Location:** `server/meetingminer/migrations/0017_thread_color_ordinal.sql:35-77`
- **Severity:** High
- **Finding:** The sequence prevents the default allocator from returning a deleted ordinal, but the record retains no history after the row is deleted. An explicit insert can therefore reuse the freed value. The `UNIQUE` constraint proves only live-row uniqueness, not the frozen guarantee that an ordinal is never recycled.
- **Evidence:** In the private migrated database, a default-created thread received ordinal `2`; after deleting that row, inserting a different thread with explicit `color_ordinal=2` succeeded and returned `2`. This is the deliberate gap documented by the builder, but it contradicts the migration header, B-40's done condition, and the spec's strict Always rule.
- **Suggested direction:** Choose one coherent contract. To preserve strict non-reuse while retaining explicit imports, add durable issued-ordinal history (for example a reservation ledger that survives thread deletion) and reject any explicit value already issued. Otherwise narrow the guarantee to "the default allocator never recycles" and explicitly authorize imports to reuse deleted values. The current spec's simultaneous requirements—strict non-reuse and arbitrary explicit import acceptance—cannot both be enforced without durable history.

Status: open; rooted in contradictory frozen-spec requirements and requires an owner decision before remediation.
