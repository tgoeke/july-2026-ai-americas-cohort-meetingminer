## Findings

### Finding 1 — Probe cleanup bypasses the shared-store writer lock

- Location: `evals/checks/gate_probe.py:246-278`
- Severity: high
- Finding: `cleanup_probe` deletes the run-owned document and node without
  taking the cross-process store file lock (and corresponding Postgres
  advisory lock) used by every projection writer. A concurrent rebuild or
  worker projection can therefore race the erasure and recreate the probe
  after cleanup has verified it absent.
- Evidence: the cleanup calls Meilisearch `delete_document` and Neo4j `DETACH
  DELETE` directly at lines 248 and 264. By contrast,
  `server/meetingminer/projections/__init__.py:619-648` holds
  `store_file_lock` and `projection_lock` around both store writes, and
  `AGENTS.md` describes that exclusion domain as covering every server
  entrypoint that writes Neo4j or Meilisearch. One concrete interleaving is:
  rebuild reads the still-published probe and waits or begins projection;
  cleanup deletes and verifies both stores; rebuild then writes its captured
  probe into one or both stores; cleanup deletes the Postgres row and reports
  all four targets verified. The result is an orphaned store artifact that the
  run report says does not exist. The delete-only textual pin constrains query
  shape but provides no concurrency exclusion.
- Suggested direction: make the cleanup participate in the same lock domain
  and lock order as projection writers for the complete delete-and-verify
  sequence, or retain an explicit single-flight rule against every dev-store
  writer. Add a deterministic concurrency regression that pauses a projection
  between its authoritative Postgres read and store write and proves cleanup
  cannot report success before that writer has completed.

### Finding 2 — The accepted subject-consumption window is not actually detected

- Location: `evals/checks/gate_probe.py:414-450,566-605` and
  `evals/harness/checks.py:1224,1296-1313`
- Severity: high
- Finding: a subject `extracted` row created on the selected moment after the
  eligibility read is published by the probe's approval, but the post-hoc
  detector silently ignores it. This violates the frozen requirement that the
  run mutate only the row it minted and invalidates the claimed detection of
  the residual window.
- Evidence: eligibility snapshots `corpus.artifacts_for(meeting_id)` before
  selecting a moment. The approve route then publishes every `extracted` row
  under that moment (`server/meetingminer/api/moments.py:617-642`). The response
  correctly places any other published id into `probe.foreign_ids`, but
  `publish_gate` reports consumption only when the foreign id exists in
  `by_id`, which is built from the still earlier subject-artifact snapshot
  passed by the check glue. A row inserted after eligibility is in neither
  snapshot, so line 1304 drops it and the check can pass after irreversibly
  publishing shared subject state. Conversely, mixing snapshots can
  misattribute a row that was `extracted` in the glue snapshot but independently
  published before this probe as consumed by the probe. The comments at lines
  1296-1300 describe the post-eligibility arrival as detected, but the data
  required to do that is absent.
- Suggested direction: close the ownership window transactionally if possible,
  or re-read and classify every foreign response id against authoritative row
  data tied to the approval outcome; a foreign row newly published by this
  request must fail loudly even when it was not in discovery. Add a race test
  that inserts a subject artifact after candidate selection and before the API
  locks pending rows, then prove it cannot be consumed silently. Also cover the
  inverse race so independently published rows are not blamed on this run.

### Finding 3 — A 409 race is judged before the winning projection finishes

- Location: `evals/checks/gate_probe.py:583-602,520-523`
- Severity: medium
- Finding: the concurrent-approval path treats the probe's Postgres
  `published` state as proof that the winning request has completed the gate,
  then reads both stores immediately. The API exposes `published` before its
  post-commit projection finishes, so a healthy overlapping run can be reported
  as a projection failure.
- Evidence: the approve route commits the lifecycle transaction at
  `server/meetingminer/api/moments.py:683` and only afterward calls
  `project_published_artifacts` at lines 691-699. During that interval a second
  request can receive `nothing-to-approve`; `_approve` re-reads `published` and
  returns `ok=True`, after which `run_gate_probe` immediately performs its post
  membership read. It can observe neither store, or only Neo4j (the projection
  writes graph before search), and `_probe_sequence_problems` reports a gate
  regression even though the winning request is still completing normally.
  The race tests make the row and both fake stores visible atomically, so they
  cannot exercise the production ordering. Because cleanup is also unlocked
  (Finding 1), it can additionally verify absence before the winner writes the
  probe back.
- Suggested direction: make the losing path wait on the projection exclusion
  domain or poll the owned id to a bounded terminal store state before judging
  the positive half, and perform cleanup only after the winner cannot still be
  projecting that id. Add a delayed-projection concurrency test that exposes
  the committed row first, holds store projection, runs the 409 path, then
  releases projection and verifies both the gate verdict and final cleanup.

### Finding 4 — The write-boundary pin admits unsanctioned query shapes

- Location: `evals/tests/test_harness_boundary.py:396-478`
- Severity: medium
- Finding: the new textual guard does not make the delete-only/direct-mint
  exception falsifiable at the promised width. It scans raw query clauses only
  in uppercase and treats every `INSERT INTO artifact` as benign, so forbidden
  mutations can be introduced while the boundary test remains green.
- Evidence: `probe_write_references` applies case-sensitive regexes for
  `MERGE`, `CREATE`, `SET`, `REMOVE`, `FOREACH`, and `UPDATE`. The equivalent
  `session.run("match ... set ...")` or `conn.execute("update artifact ...")`
  is not detected. The benign canary at line 474 explicitly admits a generic
  artifact insert, while no boundary assertion pins `_INSERT_PROBE` to the
  exact allowed columns and default `extracted` state. For example, adding a
  `state` column with value `published` to the insert still starts with the SQL
  string asserted by `test_gate_probe.py`, still carries the title parameter,
  and contains none of the forbidden uppercase clauses, but it bypasses the
  gate the probe is supposed to measure. Similarly, the guard drops the entire
  `delete` stem and therefore does not itself distinguish one-id erasure from a
  bulk/all-documents delete.
- Suggested direction: normalize parsed query text case-insensitively and
  allow-list the exact mint, one-id store-delete, one-id verification, and
  one-id Postgres-delete statement shapes rather than blacklisting a few
  tokens. Add mutation canaries for lowercase/mixed-case clauses, a probe
  inserted as `published`, multi-row inserts, and bulk or unscoped deletes.
