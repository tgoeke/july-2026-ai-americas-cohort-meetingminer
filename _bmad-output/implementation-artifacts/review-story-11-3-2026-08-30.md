## Findings

### Finding 1 — Probe cleanup bypasses the shared-store writer lock

- Location: `evals/checks/gate_probe.py:246-278`
- Severity: high
- Finding: `cleanup_probe` deletes the run-owned document and node without
  taking the cross-process store file lock (and corresponding Postgres
  advisory lock) used by every projection writer. A concurrent rebuild or
  worker projection can therefore race the erasure and recreate the probe
  after cleanup has verified it absent.
- Evidence: the cleanup calls Meilisearch `delete_document` and Neo4j `DETACH
  DELETE` directly at lines 248 and 264. By contrast,
  `server/meetingminer/projections/__init__.py:619-648` holds
  `store_file_lock` and `projection_lock` around both store writes, and
  `AGENTS.md` describes that exclusion domain as covering every server
  entrypoint that writes Neo4j or Meilisearch. One concrete interleaving is:
  rebuild reads the still-published probe and waits or begins projection;
  cleanup deletes and verifies both stores; rebuild then writes its captured
  probe into one or both stores; cleanup deletes the Postgres row and reports
  all four targets verified. The result is an orphaned store artifact that the
  run report says does not exist. The delete-only textual pin constrains query
  shape but provides no concurrency exclusion.
- Suggested direction: make the cleanup participate in the same lock domain
  and lock order as projection writers for the complete delete-and-verify
  sequence, or retain an explicit single-flight rule against every dev-store
  writer. Add a deterministic concurrency regression that pauses a projection
  between its authoritative Postgres read and store write and proves cleanup
  cannot report success before that writer has completed.
- Resolution: Fixed on the review branch. `cleanup_probe` now derives the
  production lock-file key from the configured Neo4j/Meilisearch endpoints,
  acquires that file lock first, then the `meetingminer-projections` Postgres
  advisory lock, and holds both across all four erasures and their
  verifications. If exclusion cannot be acquired, it performs no unsafe
  erasure and returns a named four-target cleanup failure. The new F1 test
  failed first with an unsupported `config` argument, then passed while
  asserting every target operation occurs inside the injected writer lock.

### Finding 2 — The accepted subject-consumption window is not actually detected

- Location: `evals/checks/gate_probe.py:414-450,566-605` and
  `evals/harness/checks.py:1224,1296-1313`
- Severity: high
- Finding: a subject `extracted` row created on the selected moment after the
  eligibility read is published by the probe's approval, but the post-hoc
  detector silently ignores it. This violates the frozen requirement that the
  run mutate only the row it minted and invalidates the claimed detection of
  the residual window.
- Evidence: eligibility snapshots `corpus.artifacts_for(meeting_id)` before
  selecting a moment. The approve route then publishes every `extracted` row
  under that moment (`server/meetingminer/api/moments.py:617-642`). The response
  correctly places any other published id into `probe.foreign_ids`, but
  `publish_gate` reports consumption only when the foreign id exists in
  `by_id`, which is built from the still earlier subject-artifact snapshot
  passed by the check glue. A row inserted after eligibility is in neither
  snapshot, so line 1304 drops it and the check can pass after irreversibly
  publishing shared subject state. Conversely, mixing snapshots can
  misattribute a row that was `extracted` in the glue snapshot but independently
  published before this probe as consumed by the probe. The comments at lines
  1296-1300 describe the post-eligibility arrival as detected, but the data
  required to do that is absent.
- Suggested direction: close the ownership window transactionally if possible,
  or re-read and classify every foreign response id against authoritative row
  data tied to the approval outcome; a foreign row newly published by this
  request must fail loudly even when it was not in discovery. Add a race test
  that inserts a subject artifact after candidate selection and before the API
  locks pending rows, then prove it cannot be consumed silently. Also cover the
  inverse race so independently published rows are not blamed on this run.
- Resolution: Fixed on the review branch. The probe now classifies the API's
  foreign published IDs against the discovery-state map at the API boundary:
  an ID discovered as `extracted`, or absent from discovery because it landed
  late, is carried separately as `consumed_foreign_ids` and fails assembly;
  an ID already discovered `published` remains report-only. The new F2 probe
  and pure-assembly tests both failed before the field/classifier existed and
  pass with the late ID named in the failure.

### Finding 3 — A 409 race is judged before the winning projection finishes

- Location: `evals/checks/gate_probe.py:583-602,520-523`
- Severity: medium
- Finding: the concurrent-approval path treats the probe's Postgres
  `published` state as proof that the winning request has completed the gate,
  then reads both stores immediately. The API exposes `published` before its
  post-commit projection finishes, so a healthy overlapping run can be reported
  as a projection failure.
- Evidence: the approve route commits the lifecycle transaction at
  `server/meetingminer/api/moments.py:683` and only afterward calls
  `project_published_artifacts` at lines 691-699. During that interval a second
  request can receive `nothing-to-approve`; `_approve` re-reads `published` and
  returns `ok=True`, after which `run_gate_probe` immediately performs its post
  membership read. It can observe neither store, or only Neo4j (the projection
  writes graph before search), and `_probe_sequence_problems` reports a gate
  regression even though the winning request is still completing normally.
  The race tests make the row and both fake stores visible atomically, so they
  cannot exercise the production ordering. Because cleanup is also unlocked
  (Finding 1), it can additionally verify absence before the winner writes the
  probe back.
- Suggested direction: make the losing path wait on the projection exclusion
  domain or poll the owned id to a bounded terminal store state before judging
  the positive half, and perform cleanup only after the winner cannot still be
  projecting that id. Add a delayed-projection concurrency test that exposes
  the committed row first, holds store projection, runs the 409 path, then
  releases projection and verifies both the gate verdict and final cleanup.
- Resolution: Fixed on the review branch. A raced approval now polls the
  owned probe until both retrieval stores reach the post-publish state before
  recording the post observation. Its bound is the configured projection
  lock budget plus the HTTP margin, and F1 still makes cleanup wait behind any
  writer that remains in flight. The F3 test exposed `published` and a 409
  before either fake store, failed after only the immediate post-read, then
  passed after the delayed store transition was observed.

### Finding 4 — The write-boundary pin admits unsanctioned query shapes

- Location: `evals/tests/test_harness_boundary.py:396-478`
- Severity: medium
- Finding: the new textual guard does not make the delete-only/direct-mint
  exception falsifiable at the promised width. It scans raw query clauses only
  in uppercase and treats every `INSERT INTO artifact` as benign, so forbidden
  mutations can be introduced while the boundary test remains green.
- Evidence: `probe_write_references` applies case-sensitive regexes for
  `MERGE`, `CREATE`, `SET`, `REMOVE`, `FOREACH`, and `UPDATE`. The equivalent
  `session.run("match ... set ...")` or `conn.execute("update artifact ...")`
  is not detected. The benign canary at line 474 explicitly admits a generic
  artifact insert, while no boundary assertion pins `_INSERT_PROBE` to the
  exact allowed columns and default `extracted` state. For example, adding a
  `state` column with value `published` to the insert still starts with the SQL
  string asserted by `test_gate_probe.py`, still carries the title parameter,
  and contains none of the forbidden uppercase clauses, but it bypasses the
  gate the probe is supposed to measure. Similarly, the guard drops the entire
  `delete` stem and therefore does not itself distinguish one-id erasure from a
  bulk/all-documents delete.
- Suggested direction: normalize parsed query text case-insensitively and
  allow-list the exact mint, one-id store-delete, one-id verification, and
  one-id Postgres-delete statement shapes rather than blacklisting a few
  tokens. Add mutation canaries for lowercase/mixed-case clauses, a probe
  inserted as `published`, multi-row inserts, and bulk or unscoped deletes.
- Resolution: Fixed on the review branch. The boundary suite now normalizes
  query whitespace, extracts the three mutation constants from the probe AST,
  and requires an exact set: the five-column/default-state mint, one-ID SQL
  delete, and one-ID Cypher delete. A case-insensitive write-query classifier
  rejects every other mutation shape. All six F4 canaries failed against the
  placeholder guard and pass now, including lowercase `SET`, mixed-case
  `MERGE`, published/multi-row inserts, and unscoped SQL/Cypher deletes.

### Finding 5 — Transient sibling probes are misclassified as subject state

- Location: `evals/checks/test_publish_gate.py:117-186` and
  `evals/checks/gate_probe.py:135-150,414-445`
- Severity: high
- Finding: overlapping runs include each other's transient probe rows in
  subject discovery and eligibility. Common interleavings therefore make a
  healthy sibling run block or make the current run report a false subject
  projection defect, contradicting the story's central claim that eval runs
  may overlap.
- Evidence: `eligible_moments` excludes a moment for every `extracted` row
  without recognizing the `eval-gate-probe-` marker. On a one-moment meeting,
  if run A mints before run B's eligibility read, B returns “every moment ...
  holds an unconsumed extracted artifact” instead of taking the documented
  concurrent-approval path. At a later timing, the glue can snapshot A's probe
  as `published`; if A cleans it before B performs membership reads, B records
  it absent and `publish_gate` reports a regression for what was merely a
  sibling's correctly erased transient row. The stranded-probe branch only
  recognizes marked rows after *all* moments are already ineligible, so it
  neither prevents these false outcomes nor distinguishes live from abandoned
  probes. Existing overlap fakes begin after both runs have effectively crossed
  eligibility and never feed a sibling probe through subject discovery.
- Suggested direction: introduce coordination or a probe-specific discovery
  model that keeps marked probe rows out of immutable subject assertions while
  distinguishing live ownership from abandoned cleanup debt. A per-moment
  lease/advisory lock held across mint, approve, assertions, and cleanup would
  allow runs to overlap across subjects while serializing the shared approval
  target. Add deterministic tests for a sibling paused (a) after mint and (b)
  after publish but before cleanup on a one-moment meeting.
- Resolution: Fixed on the review branch. Probe lifecycles now hold a
  cross-process, endpoint-and-moment-keyed file lock from the final eligibility
  check through cleanup. Runs still overlap on different moments, while a
  sibling targeting the same moment enters only after the owner has erased its
  transient row. Eligibility is re-read after acquisition, so a genuine
  subject `extracted` row remains a refusal. Both F5 tests failed before the
  coordinator/re-read existed and pass with the owner-cleanup ordering pinned.

### Finding 6 — Proven subject projection defects can be labeled not applicable

- Location: `evals/harness/checks.py:1231-1262,1364-1377`
- Severity: medium
- Finding: when probe measurement is unavailable, the result remains
  `applicable=False` even if the subject reads proved that a published artifact
  is absent from a store or cites the wrong moment. The report labels measured
  projection defects “NOT APPLICABLE.”
- Evidence: subject problems for published absence and citation failure do not
  contain the literal `GATE VIOLATION`; only unpublished presence uses that
  headline. Applicability is calculated from `probe_measured` or a substring
  search for that headline. Thus a `GateProbe(problem=..., artifact_id=None)`
  plus a published subject missing from Meilisearch yields `passed=False` but
  `applicable=False`. `CheckResult.summary()` renders that as `NOT APPLICABLE`,
  and `evals/harness/verdict.py` treats failed inapplicable blocking results
  differently from applicable failures, including excluding them from normal
  human reconciliation. The code comment says measured defects must not be
  softened this way, but the predicate covers only one defect class.
- Suggested direction: track subject observations structurally (for example a
  `subject_defect_found` boolean) and keep the check applicable whenever any
  subject gate assertion was actually evaluated and failed, independent of
  message text. Add cases for published absence and miscitation combined with
  every probe-refusal/interruption branch.
- Resolution: Fixed on the review branch. Subject assertion failures now set a
  structural `subject_defect` flag for unpublished presence, published
  absence, and published miscitation. Applicability consumes that flag rather
  than relying on a headline substring. The F6 combined-refusal test failed as
  `applicable=False` for both absence and miscitation, then passed with both
  rendered as ordinary applicable failures.

### Finding 7 — A later store error discards an already-proven gate violation

- Location: `evals/checks/gate_probe.py:366-370,493-528` and
  `evals/checks/test_publish_gate.py:173-196`
- Severity: medium
- Finding: probe and subject membership observations are built with
  all-or-nothing dictionary expressions. If an early read proves a violation
  and a later read raises, the completed observation is lost and the check
  reports only that it could not measure the gate.
- Evidence: `_membership` evaluates the Meilisearch read before the Neo4j read,
  but assignment to `pre` occurs only after the whole dictionary returns. If
  Meilisearch reports an `extracted` probe present and Neo4j raises
  `StoreAssertError`, `pre` remains `None`; the interruption path later has no
  presence to preserve as a `GATE VIOLATION`. The subject comprehension has the
  same behavior across every artifact and both stores: any later error jumps to
  `_not_applicable` and drops all earlier findings. This contradicts the stated
  rule that inability to complete measurement must never soften a violation
  already observed. Current tests fail the first membership call, so no test
  proves preservation after partial success.
- Suggested direction: accumulate observations incrementally and carry both
  partial membership and read errors into pure assembly. Judge every completed
  observation before classifying the unmeasured remainder. Add tests where the
  first store proves unpublished presence, or published absence/miscitation,
  and the second store raises for both probe and subject paths.
- Resolution: Fixed on the review branch. Probe and subject membership reads
  now write each completed observation into their result map before attempting
  the next store. A later read error is carried into assembly as the probe
  problem; subject glue deliberately skips minting after a partial subject
  read but still judges the observations already obtained. Both F7 tests
  failed by losing the first read, then passed with the first defect applicable
  and the second-store diagnosis preserved beside it.

### Finding 8 — Approval timeout is shorter than lawful projection-lock waiting

- Location: `evals/harness/retrieval.py:32,184-203` and
  `evals/checks/gate_probe.py:566-603`
- Severity: medium
- Finding: probe approval uses the 10-second generic HTTP timeout even though
  the server can wait up to 300 seconds for the projection lock. On timeout or
  another lost response, cleanup can begin while the API request is still
  committing/projecting, and the code does not reconcile the owned row unless
  the client received the specific 409 slug.
- Evidence: `approve_moment` passes `DEFAULT_TIMEOUT = 10.0` to `httpx.Client`.
  The configured projection lock wait documented in `AGENTS.md` defaults to
  300 seconds, and the approve route enters that lock-backed projection only
  after committing the row. An ordinary lock wait can therefore outlive the
  client. `approve_moment` converts the timeout to `ApproveError(slug=None)`;
  `_approve` records failure immediately, then `run_gate_probe` reads and
  deletes while the server handler may continue. A response lost after commit
  has the same ambiguity. The 409 tests do not cover this path and no fake
  keeps a server-side operation alive after the client fails.
- Suggested direction: give this mutating call a timeout consistent with the
  projection-lock contract and treat every ambiguous POST outcome as unknown
  until the owned row and the writer exclusion domain are reconciled. Cleanup
  must not start while that request can still project. Add a test with a held
  projection lock/client timeout and another with a committed successful
  response dropped before delivery.
- Resolution: Fixed on the review branch. Probe approval now passes the
  projection-lock budget plus a ten-second response margin, rather than the
  generic ten-second read timeout. Every `ApproveError` is reconciled against
  the owned row: a published row becomes an explicitly ambiguous completed
  mutation and takes the F3 wait path; an unpublished row remains a refusal.
  Both F8 tests failed first (missing timeout argument and unreconciled lost
  response) and pass with cleanup verified.

### Finding 9 — Cleanup verification violates the single store-read boundary

- Location: `evals/checks/gate_probe.py:196-225,261-273`
- Severity: medium
- Finding: the cleanup module performs direct Meilisearch and Neo4j reads even
  though the frozen contract says there are no store reads outside
  `harness/stores.py`'s read-only helpers. The new exception is therefore wider
  than the specified delete-only write sanction.
- Evidence: `_search_absent` calls `search.index(...).get_document` directly,
  and graph verification opens a driver session and executes `_NODE_PRESENT`
  directly. The module documentation claims `harness/stores.py` remains the
  sole store-read module, but the import guard sees no Neo4j import because the
  driver is duck-typed, and the write-stem scan does not detect reads. Existing
  `stores.artifact_in_search` and `stores.artifact_in_graph` already implement
  the read-only access modes, response-shape handling, and named error
  conversion intended to keep these observations centralized.
- Suggested direction: delegate post-delete verification to read-only helpers
  in `harness/stores.py` (extending their result/error contract if absence after
  deletion needs distinct wording) and keep `gate_probe.py` limited to the
  narrowly sanctioned delete calls plus ownership orchestration. Extend the
  boundary guard to detect direct store method/session reads from the probe
  module, including duck-typed driver use.
- Resolution: Fixed on the review branch. Cleanup retains the sanctioned
  Meilisearch/Neo4j delete calls but now verifies both targets exclusively via
  `stores.artifact_in_search` and `stores.artifact_in_graph`. The duplicate
  `get_document` and graph verification query were removed, so read access
  modes and store errors have one implementation again. The F9 boundary test
  failed on both direct-read markers and passes while asserting both delegated
  calls remain present.

### Finding 10 — An ambiguous autocommit insert can strand an unidentifiable probe

- Location: `evals/checks/gate_probe.py:471-490`
- Severity: medium
- Finding: the probe is inserted on an autocommit connection and its UUID is
  learned only after `execute(... RETURNING id)` completes. A connection loss
  after the server commits but before the result reaches the client leaves a
  real probe row whose id is unavailable to the cleanup/report path.
- Evidence: `artifact_id` is assigned only from `fetchone()` at line 490, and
  the cleanup `try/finally` begins afterward. Psycopg cannot make a failed
  client acknowledgement prove that an autocommit statement did not commit.
  In this window `_record` reports only the raised database exception; the row,
  title marker, and exact UUID never reach `GateProbe` or `CleanupReport`. This
  contradicts the module's claim that only process death can outlive cleanup
  and the frozen rule that leftovers are loud with exact ids. Fake connections
  make insert and returned id indivisible, so the path is untested.
- Suggested direction: separate insert from commit so the Postgres-minted UUID
  is received before commit, retain that id across an ambiguous commit, and
  perform cleanup/reconciliation from a fresh connection when the original is
  unusable. Alternatively add a unique run/subject ownership token that allows
  deterministic recovery without weakening AD-6. Test commit acknowledgement
  loss with a row that is visible from a second connection.
- Resolution: Fixed on the review branch. Minting now uses a non-autocommit
  transaction, captures the Postgres UUID, and explicitly commits before the
  connection enters autocommit mode for the remaining sequence. A commit
  acknowledgement loss preserves that UUID, rolls back the uncertain session,
  and performs locked cleanup through a fresh connection. The F10 tests failed
  first on `autocommit=True` and the missing recovery path, then passed with the
  second connection observing and deleting the shared row.

### Finding 11 — Operational docs lift the serial rule before the claim is true

- Location: `AGENTS.md:79,123-145`,
  `.claude/skills/integrate/dispatch.md:32-36`, and
  `evals/RUNBOOK.md:98-107`
- Severity: high
- Finding: the authoritative operating guidance tells agents to overlap eval
  runs and says a concurrent approval is “never a failure” before the owner-run
  measurement has occurred, despite implementation races that can fail runs or
  leave orphaned store state. `AGENTS.md` also contradicts itself twice about
  whether evals remain serial.
- Evidence: the new bullet at `AGENTS.md:123` permits overlap and promises race
  success, while line 79 still says “the remaining limit is `make evals-run`”
  and lines 143-145 still say per-run namespaces are needed before runs can
  overlap. Dispatch now uses the permissive statement to approve parallel
  candidate pairs, and the RUNBOOK says runs “do not contend.” The spec's own
  Verification section says the live two-run measurement was not run. Findings
  1, 3, 5, and 8 statically demonstrate interleavings in which the promised
  outcome is false. The RUNBOOK and README also say the probe is “minted through
  the public api,” but the implementation mints it with direct SQL and uses the
  API only for approval.
- Suggested direction: keep the single-flight operational rule until the
  concurrency findings are fixed and the owner-run procedure observes the real
  stack. Then update every serial/permissive passage as one coherent change,
  state direct-SQL mint plus public-API approval accurately, and qualify the
  exact writers/runs that may overlap based on the lock design actually built.
- Resolution: Fixed on the review branch. `AGENTS.md`, integration dispatch,
  and the RUNBOOK now agree that `make evals-run` remains single-flight against
  another eval run and dev-store writers until the owner records the live
  two-run procedure. They distinguish fake-proven ownership/coordination from
  operational acceptance and no longer promise that every concurrent race is
  harmless. The F11 docs-contract test failed on the permissive text and now
  passes. The live acceptance itself remains an explicit owner action; this
  review did not and must not run `make evals-run`.

### Finding 12 — The in-scope AD-16 boundary documentation remains false

- Location: `evals/README.md:9-28,67-69` and
  `evals/RUNBOOK.md:44-46,98-100`
- Severity: medium
- Finding: the primary eval reference still says the harness mutates only
  through the public API, opens Postgres only read-only through `corpus.py`, and
  confines store access to `stores.py`. Story 11.3 deliberately violates each
  statement but does not update the governing explanation of the boundary.
- Evidence: `gate_probe.py` imports `psycopg`, opens a writable connection,
  inserts/deletes the artifact directly, calls Meilisearch deletion directly,
  and opens Neo4j sessions for delete and verification. README lines 9-28 still
  present the old rule as AST-enforced fact; its file map and the RUNBOOK also
  say the probe is “minted through the public api,” although only approval uses
  that endpoint. The spec defers an architecture-spine amendment to integration,
  but README/RUNBOOK are explicitly in this story's footprint and now give
  reviewers/operators an inaccurate account of the sanctioned exception.
- Suggested direction: update the in-scope reference and procedure to state
  the exact direct-SQL mint, API approval, and delete-only cleanup exception,
  including where read verification lives after Finding 9. Make the boundary
  guard description match what it mechanically enforces, while retaining the
  deferred AD-16 spine amendment for integration.
- Resolution: Fixed on the review branch. README and RUNBOOK now describe the
  exception as direct SQL for one run-marked `extracted` row and its
  Postgres-minted UUID, public-API approval, and writer-locked delete-only
  cleanup of that UUID. They state that all cleanup verification delegates to
  `harness/stores.py` and retain the architecture-spine amendment as integration
  work. The F12 docs-contract test failed on the missing terms and obsolete
  “minted through the public api” claim, then passed against both documents.
