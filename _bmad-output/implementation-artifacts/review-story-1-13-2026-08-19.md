## Verdict

**Does not pass review as it stands.** The re-emit path can write a drop that intake rejects and then report it current, and accepted recovery/participant combinations can discard or mismatch previously processed evidence. A live `--re-emit` write-and-POST pass remains unexercised.

Focused verification after remediation: `make puller-test` (102 passed) and `uv run --project server pytest server/tests/test_augmentation.py server/tests/test_ingests.py server/tests/test_drop_schema.py` (84 passed, one pre-existing deprecation warning). ## Findings

### 1. Contract decision — recovered VTT/TXT is promised by re-emit but has no intake path

- **Severity:** high
- **Location:** `pull_transcript/emit-drop.js:503-514`; `server/meetingminer/api/ingests.py:358-400`
- **Claim:** The frozen matrix permits a re-emit for a newly available canonical evidence file, but intake accepts only a new recording or a non-empty participant graph.
- **Failure scenario:** A newest drop already has participants and `transcript.txt`; the archive later gains `transcript.vtt`. `dropIsCurrent()` sees a missing planned file and writes `-003`. The incoming drop adds neither a recording nor participants, so `_check_augmenting_drop()` returns `409 augment-adds-nothing`; the CLI calls that `already ingested`.
- **Evidence:** The matrix says a re-emit occurs for a canonical evidence file the newest drop lacks. `dropIsCurrent()` tests every `plan.files` entry, whereas `adds_recording` and `adds_participants` are the only accepted evidence classes.
- **Route:** decision needed. Either extend the intake contract and stage re-arm semantics to supplied transcript files, or restrict re-emit planning to the two supported kinds. The implementation must not choose silently.

**Resolution, 2026-08-19:** Restrict `--re-emit` to the two evidence kinds intake already accepts: a recording the target lacks and a non-empty participant graph the target lacks. A VTT/TXT-only change must not create or POST a sibling drop. This finding is now a patch item.

### 2. A graph re-emit may discard a transcript the target already contains

- **Severity:** high
- **Location:** `pull_transcript/emit-drop.js:503-514`
- **Claim:** Re-emit validates only that the old drop contains all files in the new plan, not that the new plan preserves every transcript the old target contains.
- **Failure scenario:** The base drop contains `transcript.txt` and `transcript.vtt`; the current occurrence retains only TXT but gains an org chart. `emitDrop(..., reEmit: true)` finalizes `-002` without VTT. Intake rejects it under the AD-13 transcript-preservation guard, but the next run sees `-002` as graph-bearing and returns `current`; the job remains on the old drop.
- **Evidence:** `_check_meeting_replacement()` rejects missing target transcripts at `ingests.py:490-496`. No preflight in `dropIsCurrent()` or `emitDrop()` checks the inverse file set. Existing tests cover only the retained-file path.
- **Route:** patch now. Preflight the candidate against the newest target's required canonical evidence before finalizing, and add this loss-of-VTT regression.

### 3. A refused or failed re-emit POST becomes an unrecoverable-looking `current` drop

- **Severity:** high
- **Location:** `pull_transcript/emit-drop.js:663-667`, `835-849`
- **Claim:** The CLI treats every 409 as an already-ingested duplicate and gives a retry command that posts the base drop rather than the failed sibling.
- **Failure scenario:** A just-written `-002` times out, gets a 422, or gets `409 augment-target-incomplete`/`augment-adds-nothing`. It remains write-once. The emitted retry command runs without `--re-emit`, returns the base `exists` result, and POSTs that old path; a subsequent `--re-emit` returns `current` and deliberately posts nothing. The participant graph never reaches the existing job.
- **Evidence:** `postIngest()` maps all 409s to `duplicate`; only `current` skips the POST. The re-emit tests do not exercise a failed/retried HTTP handoff, and the normal POST test has no re-emit sibling.
- **Route:** patch now. Recognize only the duplicate-source problem as benign; make non-duplicate 409s fail visibly; and provide a direct retry for the exact finalized sibling (with HTTP-backed tests).

### 4. Recording recovery can erase a previously accepted participant graph

- **Severity:** high
- **Location:** `server/meetingminer/api/ingests.py:467-496`
- **Claim:** The immutable replacement checks preserve recordings and transcripts but not an existing non-empty participant graph.
- **Failure scenario:** A transcript-only meeting first receives a graph and becomes mail-keyed. A later recording-recovery augment includes required transcripts and MP4 but no `participants`. Intake accepts it because the target lacks a recording, changes the job's drop path, and re-runs `align`; `align` now follows its graph-absent fallback and replaces the roster with transcript-label/name identities.
- **Evidence:** `_check_meeting_replacement()` only verifies recording, corpus, clock fields, and transcripts. The accepted drop becomes the only drop read by `align`.
- **Route:** patch now. Preserve the graph as an immutable input for a recovery, or refuse a graph-shedding recovery; add an end-to-end regression.

### 5. A changed recording can be accepted under the narrow participant-only re-arm

- **Severity:** high
- **Location:** `server/meetingminer/api/ingests.py:358-400`, `575-580`
- **Claim:** A new participant graph lets an augmenting drop replace an already-recorded meeting's MP4 without re-running the video pipeline.
- **Failure scenario:** The target already has recording A and no graph. An incoming augment has a different recording B, the required transcripts, and a new graph. `adds_participants` is true while `adds_recording` is false, so only `align` and `moments` are queued. The job points at B but frames, OCR, screens, and STT still describe A.
- **Evidence:** The check requires only that an already-recorded meeting carry *a* recording, not the same recording; stage selection turns solely on `not target_has_recording`.
- **Route:** patch now. Require a non-recovery recording to match the target, or define a full replacement/reprocessing flow deliberately.

### 6. Concurrent augmentations can both succeed and lose one accepted graph

- **Severity:** medium
- **Location:** `server/meetingminer/api/ingests.py:257-271`, `509-533`
- **Claim:** Augmentation reads and re-arm updates are not serialized per target occurrence.
- **Failure scenario:** Two graph-bearing `-002`/`-003` requests arrive while the target is complete and graph-less. Both read the same target state and pass the gate; both return 200, and the later job update overwrites `drop_path`. The first accepted graph is never processed.
- **Evidence:** `_augment_target()` performs an unlocked select and `_rearm_job()` unconditionally updates the job. The unique source-id conflict path does not cover an in-place re-arm.
- **Route:** patch now. Lock the target job/meeting or use a conditional transition, then test that the second request observes the first re-arm rather than succeeding.

### 7. The migration summary marks an empty graph as migrated

- **Severity:** medium
- **Location:** `pull_transcript/emit-drop.js:539-545`
- **Claim:** The progress reporter uses `participants` key presence, although the intake and re-emit predicates define `participants: []` as no graph.
- **Failure scenario:** A valid externally created newest drop has `participants: []`. It provides no mail-keyed roster, but `unmigratedPrefixes()` does not include it in `stale` and can report a completed migration.
- **Evidence:** `dropIsCurrent()` and `_has_participant_graph()` require a non-empty array; `unmigratedPrefixes()` tests only `'participants' in metadata`.
- **Route:** patch now. Share the non-empty-graph rule in the summary and add a regression test.

### 8. The required chart read-error behavior has no regression test

- **Severity:** low
- **Location:** `pull_transcript/test/emit-drop.test.js:1348-1358`
- **Claim:** The suite omits the non-ENOENT read-error branch for the chart.
- **Failure scenario:** If `readParticipantGraph()` regresses to throw for a directory or unreadable file at `<stem> org chart.json`, the transcript-only occurrence fails instead of warning and emitting without participants.
- **Evidence:** The tests cover malformed JSON and unusable content but do not exercise `readFileSync` failing on a present path.
- **Route:** patch now. Create a portable directory-at-chart-path fixture and assert warning plus successful graph-less emission.
