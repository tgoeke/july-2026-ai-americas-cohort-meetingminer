## Design decisions to attack

State these as choice + assumption, not settled facts:

1. **A hand-rolled `fetch` SSE reader instead of the generated
   `client.sse.post`.** Choice: `chatStream.ts` bypasses the generated
   client's SSE machinery entirely and does its own `fetch`/stream parsing.
   Assumption: the generated client's default infinite-retry-on-error
   behavior (`web/src/client/core/serverSentEvents.gen.ts:135,228`) is wrong
   for a permanent `422` gate rejection, and no simpler option (e.g. passing
   `sseMaxRetryAttempts: 0`) was viable because the generated client also
   discards the response body on a non-2xx status, losing the `reason`
   extension. Attack whether that tradeoff was necessary or whether a
   thinner change to the generated-client call site would have sufficed.
2. **Citations always navigate to the moment view by `momentId` alone — no
   branch on `screenshotId`/`sourceDeepLink`.** Assumption: `MomentView`
   (Story 2.2) already renders the transcript-only degraded mode itself, so
   duplicating that branch here would be redundant. Attack whether that
   assumption actually holds by reading `MomentView.tsx`'s current behavior,
   not by trusting the spec's claim.
3. **No inline citation-to-claim linkage; citations render as a flat list
   below the answer, in server-given (first-appearance) order.** Assumption:
   AD-15's citation contract is a flat array by design, and the frozen
   story-3.3 spec's own matrix calls it "first-appearance order" — so
   re-sorting or inline-anchoring on the client would misrepresent the
   contract, not improve it. Attack whether "Chat UI with ... Replay
   Citations" in the story title implies more per-claim linkage than this
   delivers.
4. **A stream that ends without a `chat.done` frame is now treated as a
   failure, not a silent partial success (patched in `459a709`).** Assumption:
   any answer the client didn't see fully replayed is untrustworthy, even
   though everything received so far came from an already-validated answer.
   Attack whether discarding a mostly-complete answer is the right call
   versus, say, showing it with a "connection interrupted" caveat. **This is
   the finding an integration reviewer flagged as the one most worth a second
   pair of eyes on**: silent partial success is a failure mode this repo has
   hit before, through a different door — the 4-1a extraction stage hit the
   same shape. Confirm the test added for this in `459a709` (a stream that
   emits `chat.token`/`chat.citations` and closes with no `chat.done`) really
   pins the fix, not just the happy path around it.
5. **Submit is no longer gated on `busy` (patched in `459a709`, changed from
   the original `b6825d6` implementation).** A re-submit while a question is
   in flight now aborts the prior stream via the existing `AbortController`
   guard rather than being disabled. Attack whether this was fully threaded
   through — in particular whether the UI gives any visible signal that an
   in-flight question was abandoned versus completed, and whether the
   `doneReceived` guard interacts correctly with an abort that lands in the
   same tick as the stream's natural end.
6. **A 60-second client-side timeout on `/chat`, with no automated test**
   (see Residual risks in the spec's `## Auto Run Result`) — the implementer
   judged `AbortSignal.timeout`'s internal timer unreliable under vitest fake
   timers and left this path verified by code inspection only. Attack
   whether that's an acceptable gap or whether a controllable-timer approach
   (e.g. injecting the timeout signal rather than constructing it internally)
   was available and skipped.
7. **`chatStream.ts` hand-builds the `/chat` request body rather than going
   through the generated `askCorpus` operation.** The hand-rolled reader is
   justified — the generated SSE client discards the error body and retries
   forever, which is genuinely wrong for a permanent `422` gate rejection,
   and doubling a config-bound `Llm(chat)` call to work around it would be a
   real cost. But name the consequence: because the request is hand-built,
   the outgoing `{question}` body is not type-bound to `AskCorpusData` the
   way `askCorpus()` would enforce it, so a future server-side contract
   change to the request shape would not necessarily fail this build.
   Citations *are* type-bound (`chatStream.ts` imports `CitationModel`/
   `RouteModel` from the generated types), so the gap is narrow — request
   body only. This sits next to a standing deferred item from story 1.10:
   `make check-client` only asserts the three `.gen.ts` files exist, it is
   not a staleness detector. Decide whether that gap needs a test here or is
   better closed at the `check-client` level instead.
