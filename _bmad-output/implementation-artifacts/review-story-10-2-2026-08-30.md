## Findings

### F1 — A backfilled earlier topic changes the durable thread id (resolved — owner-directed patch)

- **Location:** `<intent-contract>` “Always” idempotency rule in `_bmad-output/implementation-artifacts/spec-10-2-threads-and-the-graph-projection.md`; `server/meetingminer/domain/threads.py:25-32`, `server/meetingminer/domain/threads.py:267-280`, `server/meetingminer/domain/threads.py:435-438`; `server/meetingminer/migrations/0015_threads.sql:18-31`, `server/meetingminer/migrations/0015_threads.sql:108-123`
- **Severity:** Medium
- **Finding:** The promised identity is stable only for an unchanged topic set. If an older meeting is backfilled with a differently named topic that joins an existing cluster by embedding, that new topic becomes the chronological seed, changes `identity_key`, causes a new `thread` row/id to be upserted, moves the old memberships, and lets the last-link trigger delete the old thread. That invalidates the id future 10.2a curation is expected to attach to and leaves the old graph node until a full rebuild. The risk is explicitly acknowledged in the planner notes, but the chosen identity remains the frozen contract, so this review cannot safely repair it in code.
- **Evidence:** `cluster_topics` derives `identity_key` solely from the minimum topic under `(meeting.started_at, meeting.id, normalized name, topic.id)`. `_upsert_thread` conflicts only on that key; `_upsert_membership` then moves each topic, and `delete_thread_when_last_topic_removed` deletes the emptied old row. No alias, supersession record, or stable cluster identity links the replacement id to the prior id. This is not the unchanged-rerun case covered by `test_a_rerun_over_unchanged_topics_yields_the_same_threads`.
- **Suggested direction:** Owner/spec decision before 10.2a: either define thread identity independently of the mutable chronological seed, preserve an explicit old→new identity/alias that curation follows, or formally constrain/backstop backfills and document how curation survives re-seeding. Add a regression for an earlier embedding-linked backfill once that policy is chosen.
- **Resolution:** The owner ruled on 2026-08-30 that identity comes from normalized cluster content, not chronology. Commit `e2d7033` selects the content candidate independently of meeting time and reuses a row already attached to a cluster member before minting. The new regression failed with different UUIDs on the rebased pre-fix code and passes with both topics attached to the original UUID.

### F2 — Thread “mention” timestamps use moment starts instead of mention anchors (patch)

- **Location:** `server/meetingminer/projections/traversals.py:588-615`, `server/meetingminer/projections/traversals.py:714-733`, `server/meetingminer/projections/traversals.py:759-770`; `server/tests/test_projections_threads.py:226-266`
- **Severity:** Medium
- **Finding:** `ThreadMention.started_at`, and therefore the thread-level `first_mention_at` / `last_mention_at`, are populated from `Moment.startedAt`. A topic mention already carries the more precise meeting-relative `anchorMs`; for a mention late inside a long moment, the returned “mention timestamp” is the beginning of the containing moment rather than when the mention occurred.
- **Evidence:** `_THREAD_TIMELINE_CYPHER` returns both `men.anchorMs` and `mo.startedAt`, but `_moment_started_at` parses only the latter into `ThreadMention.started_at`; the final aggregate takes min/max of that field. The extraction record defines `topic_mention.anchor_ms` as the actual anchor within the meeting, while `moments.py` defines `moment.started_at` as `meeting.started_at + moment.start_ms`. Existing aggregate tests set `anchorMs` different from `startMs` but still expect the moment start, so they encode the bug rather than detecting it.
- **Suggested direction:** Compute the mention wall clock as the validated meeting start plus `anchorMs`, keep moment start/end on `TraversalMoment` for rendering/span purposes, and add a regression where multiple anchors differ materially from their containing moment starts.

### F3 — Exact pair generation repeats vector norms and retains every pair score (patch)

- **Location:** `server/meetingminer/domain/threads.py:147-169`, `server/meetingminer/domain/threads.py:203-217`, `server/meetingminer/domain/threads.py:250-280`, `server/meetingminer/domain/threads.py:296-325`
- **Severity:** Medium
- **Finding:** The O(n²) design is implemented with substantially more CPU and memory than exact clustering requires. Every pair recomputes both 1,024-dimensional norms, then both directed copies of every score are retained even though membership records only need each topic’s maximum qualifying similarity. At the documented target of hundreds of meetings × several topics, this becomes millions of Python-level vector scans plus an O(n²) dictionary.
- **Evidence:** A local deterministic probe on this branch took 7.743s for just 500 topics × 1,024 dimensions (124,750 pairs); 2,500 topics imply 3,123,750 pairs. Each current call performs three full vector passes (two norms and one dot), and `similarities[(left,right)]` plus `similarities[(right,left)]` retains 6,247,500 entries at 2,500 topics. The comment’s “few hundred thousand short dot products, cheaper than the read” does not describe the configured 1,024-dimensional vectors or the stated upper corpus shape.
- **Suggested direction:** Preserve deterministic exact all-pairs comparison, but normalize each vector once, perform one dot product per pair, and retain only each topic’s best score at or above the threshold (any non-name member necessarily has one). Add a structural regression proving norms scale with topics, not pairs; no approximate index or recall trade-off is needed.

### F4 — Non-finite embedding components fail open as maximum similarity (patch)

- **Location:** `server/meetingminer/domain/threads.py:147-169`, `server/meetingminer/domain/threads.py:172-202`, `server/meetingminer/domain/threads.py:278-297`
- **Severity:** High
- **Finding:** `NaN` or infinite values from an embedder are not validated. Python’s `min(1.0, nan)` returns `1.0`, so the clamp converts a non-finite cosine into maximum similarity and can union unrelated topics. The optimized normalization path has the same outcome (`nan` unit components → `nan` dot → `1.0`). This is the exact silent-whole-corpus failure the threshold guard says must fail closed.
- **Evidence:** On the review branch, `cosine_similarity((nan, 0), (1, 0))` evaluates to `1.0`. The embedder port validates vector width but not component finiteness, and neither `cosine_similarity` nor the derivation validates it. An invalid provider response is therefore accepted as the strongest possible link instead of producing a named refusal.
- **Suggested direction:** Reject any non-finite component (and any non-finite computed norm) with `ThreadDerivationError` before pair generation. Cover both the public cosine helper and the production `cluster_topics` path with `NaN`/±infinity regressions.

### F5 — Replacing one meeting’s topics remints unchanged singleton threads (resolved — owner-directed patch)

- **Location:** `<intent-contract>` “No orphans at the record” rule in `_bmad-output/implementation-artifacts/spec-10-2-threads-and-the-graph-projection.md`; Story 10.1 rerun contract in `_bmad-output/implementation-artifacts/spec-10-1-topic-extraction.md`; `server/meetingminer/migrations/0015_threads.sql:102-123`; `server/meetingminer/domain/threads.py:498-579`
- **Severity:** High
- **Finding:** Story 10.1 replaces every `topic` row for a meeting on extraction rerun. For a thread whose only member is an otherwise unchanged topic in that meeting, the cascade removes its last `topic_thread` row and migration 0015 immediately deletes the thread. When derivation runs over the replacement topic row, the same `identity_key` is inserted with a new UUID. Therefore changing an unrelated topic in the same meeting remints the unchanged singleton thread and breaks any curation or external reference attached to its old id.
- **Evidence:** A review-only Postgres probe created one meeting with independent “Vendor feed” and “Budget review” topics, derived threads, captured the vendor thread UUID, then simulated Story 10.1’s replace-all rerun with “Vendor feed” unchanged and “Budget review” replaced by “Release plan”. After derivation, `vendor feed` had UUID `01a0557d-79ea-71b4-9f34-ac08bb5012ad` instead of `01a0557d-79e7-762a-8edf-f9ee6436318f`; the preservation assertion failed. The existing unchanged-rerun test never deletes/reinserts `topic` rows, so it cannot expose this integration path.
- **Suggested direction:** Owner/spec decision before production wiring or 10.2a: reconcile replace-all topic writes with durable thread identity. Options include deferring orphan deletion across the replacement+derivation unit, preserving tombstoned thread identities for reuse, or attaching curation to a durable alias independent of the ephemeral thread row. The chosen rule needs a red-to-green regression for an unrelated same-meeting topic change.
- **Resolution:** The owner ruled on 2026-08-30 that membership cannot control identity lifetime. Commit `e2d7033` removes eager orphan enforcement from migration 0015 and retains empty rows for content-key reuse. The review-only probe became a permanent regression: it failed with distinct before/after UUIDs on the rebased pre-fix code and now preserves the identical UUID. The ordinary unchanged-rerun test never deletes and reinserts topic rows, so it cannot expose this path.

### F6 — Deferred traversal is reported as unregistered at runtime (patch)

## Design-decision rulings

1. The unchanged-input partition and upsert design is structurally idempotent, the content-key collision guard is executed before writes, and F7 observes both no-op conflict clauses. F1/F5 extend that identity evidence across corpus growth and Story 10.1 replacement.
2. Chronology now controls presentation only. Identity candidates come from normalized cluster content, and an already-linked row wins before minting, so an older embedding-linked backfill preserves `thread.id` (F1).
3. `thread-timeline` is safely registered but unreachable from chat: it is absent from the classifier prompt and rejected before `_traversal_leg`. The declaration/tripwire is sound; only its observable fallback taxonomy was wrong (F6, fixed).
4. Meeting-scoped `Topic` and cross-meeting `Thread` follow the existing `Artifact`/`Screen` asymmetry. An edgeless graph `Thread` lingering until `rebuild --all` is the explicitly accepted behavior, not a finding.
5. The derivation reads, embeds, then writes. The embedder-down test catches a reordered write because `pytest.raises` consumes the exception before the pool context exits, so any pre-error write would commit and fail the zero-row assertion. No silent name-only fallback was found.
6. The unmeasured `0.82` value and the `0.5` fail-closed floor are honestly recorded choices in the frozen contract. F8 now makes the stated loader bounds executable verification; threshold quality still needs later corpus measurement.
7. Exact O(n²) pair coverage remains deterministic, but F3 removes repeated norms, Python-level dot loops, and O(n²) score retention. The deterministic 500-topic × 1,024-dimension probe improved from **7.743s** to **0.527s** while preserving exact comparisons.
8. `linked_by` is a property of the completed cluster. For a non-name member, retaining its maximum qualifying similarity is sufficient: such a member necessarily has at least one `>= threshold` edge, so no discarded below-threshold score could be the maximum.
