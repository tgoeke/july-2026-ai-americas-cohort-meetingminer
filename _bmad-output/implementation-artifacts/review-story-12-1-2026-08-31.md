## Scope

Adversarial review of Story 12.1, including the exact-byte retention contract,

## Findings

### F1 — `documentText` is optional in the generated client, weakening `null` versus `""` [medium] [open]

- Anchor: `server/meetingminer/api/extraction.py:135`; generated evidence:
  `web/src/client/types.gen.ts:728`.
- Requirement: the Story 12.1 contract says an unretained pre-12.1 document is
  `null`, an honestly empty retained document is `""`, and those two facts stay
  distinct in the column, on the wire, and in the client contract.
- Finding: `ExtractionDocument.document_text` is declared with a default of
  `None`. Pydantic therefore omits it from the OpenAPI schema's `required`
  array, and the generated client exposes `documentText?: string | null`.
  Although the current route constructor supplies the field at runtime, a
  TypeScript consumer is told that omission is a supported third state and is
  not forced to handle the retention distinction.
- Concrete failure: a renderer can compile while treating `undefined` as its
  ordinary missing-property case, so a response contract regression that drops
  `documentText` remains type-correct and can present a pre-retention row like
  an empty document. This defeats the AD-18 distinction the story explicitly
  depends on.
- Required remediation: make `documentText` required-but-nullable in OpenAPI,
  regenerate the client from the local schema without starting the shared API,
  and pin both the schema requirement and generated non-optional TypeScript
  shape. Keep `null` and `""` behavior unchanged.
- Red-first evidence: pending.

### F2 — 404 and 409 problem bodies generate as `unknown` [medium] [open]

- Anchor: `server/meetingminer/api/extraction.py:95`; generated evidence:
  `web/src/client/types.gen.ts:3610`.
- Requirement: API failures are RFC 9457 `application/problem+json`, and this
  route declares `ProblemDetails` for its not-found and not-viewable outcomes.
- Finding: the 404 and 409 response entries combine `model: ProblemDetails`
  with an empty custom `application/problem+json` content object. FastAPI puts
  the model schema under `application/json` while leaving the actual runtime
  media type schema-less. The generated client consequently emits `404:
  unknown` and `409: unknown`; only 422 is typed as `ProblemDetails`.
- Concrete failure: a web consumer cannot safely read the stable problem
  `type`, `detail`, or extensions for the endpoint's two principal failures,
  even though runtime tests prove those bodies exist. The existing tests do not
  inspect the OpenAPI response schemas, so this shipped green.
- Required remediation: declare the `ProblemDetails` reference directly under
  `application/problem+json` for 404 and 409, pin all three error schemas in an
  OpenAPI contract test, and regenerate the TypeScript client locally.
- Red-first evidence: pending.

### F3 — An unencodable generated reply bypasses the named retention refusal [medium] [open]

- Anchor: `server/meetingminer/pipeline/stages/extract.py:468` and
  `server/meetingminer/pipeline/stages/extract.py:932`.
- Requirement: the exact bytes retained are the bytes parsed, and unusable
  extraction input fails by name with the affected document identified.
- Finding: both `_digest_of` and `_retained_text` call `text.encode("utf-8")`
  without translating `UnicodeEncodeError`. A JSON provider response can
  contain an escaped lone surrogate, which Python represents as a `str` but
  UTF-8 cannot encode. The failure occurs in `_digest_of` before the retention
  guard and is recorded as `unexpected UnicodeEncodeError`, without the
  document kind.
- Concrete failure: a generated `arch-summary` containing `\\ud800` fails the
  meeting without the promised document-specific refusal, making the operator
  infer which of four model passes produced the unusable text. Direct
  reproduction against the subject branch yielded `UnicodeEncodeError:
  surrogates not allowed`.
- Required remediation: centralize UTF-8 encoding behind a helper that converts
  this failure to `StageError` naming the document, use it for generated digest
  and retention verification, and add a worker regression test using a lone
  surrogate in parser-ignored prose.
- Red-first evidence: pending.

### F4 — The route calls model output evidence, contradicting amended AD-4 [low] [open]

- Anchor: `server/meetingminer/api/extraction.py:174`; architecture anchor:
  `docs/architecture.md:114`.
- Requirement: amended AD-4 defines an extraction document as a claim *about*
  evidence, never evidence itself and never a citation target.
- Finding: the route's public OpenAPI description says, "The document a run
  produced is the evidence for the artifacts it yielded." That is the exact
  classification AD-4 rejects.
- Concrete failure: generated SDK documentation teaches a later consumer that
  the document can prove a meeting claim, inviting the circular citation path
  Story 12.4 is explicitly required to prevent.
- Required remediation: describe the document as the source record for the
  extraction run and explicitly preserve AD-4's claim-about-evidence boundary;
  pin the public operation description so it cannot drift back.
- Red-first evidence: pending.

### F5 — A rerun can orphan surviving approved artifacts from their retained source document [high] [decision needed]

- Anchor: `server/meetingminer/pipeline/stages/extract.py:377-379`,
  `server/meetingminer/pipeline/stages/extract.py:488-493`, and
  `server/meetingminer/pipeline/stages/extract.py:529-548`.
- Conflicting requirements: Story 4.1's settled rerun behavior preserves an
  approved moment's entire artifact set, including sibling drafts; Story 12.1
  requires the one `(meeting_id, kind)` document row to be replaced on every
  rerun alongside the artifacts derived from it.
- Finding: the stage skips every proposal on an approved moment, preserving
  those prior-run artifact rows, but unconditionally upserts the new document
  text into the same source row. The old text is lost. An approved or published
  artifact can therefore survive while the only readable document for its kind
  is a later reply that did not produce it.
- Concrete failure: after approving a decision and rerunning extraction with a
  changed architecture-summary reply, the endpoint serves only the new reply
  beside the surviving old decision. A reader cannot inspect what the model
  actually wrote when it produced the approved artifact—the provenance purpose
  of retaining the document is defeated for the highest-value rows.
- Why open: no patch preserves both frozen contracts without a product/schema
  choice. Versioned extraction-source rows plus an immutable artifact-to-source
  reference preserve provenance but contradict the specified single-row
  replacement shape; freezing a whole document kind once any artifact is
  approved prevents fresh extraction elsewhere; overwriting approved artifacts
  violates the existing lifecycle contract. Owner decision required.

### F6 — The exact-byte refusal and database length guard lack negative verification [medium] [open]

- Anchor: `server/meetingminer/pipeline/stages/extract.py:919` and
  `server/meetingminer/migrations/0019_extraction_document_text.sql:55`.
- Requirement: exact-byte identity is the story's primary acceptance clause,
  including the two-read adopted-document path and the database's independent
  length equality.
- Finding: every current checksum assertion starts from matching text, digest,
  and size. No test presents a same-length digest mismatch to `_retained_text`,
  simulates different bytes between `sha256_and_size(path)` and
  `path.read_bytes()`, or attempts a direct retained-row insert whose
  `byte_size` disagrees with `octet_length(document_text)`.
- Concrete failure: mutating the application guard to length-only, removing the
  migration CHECK, or allowing a changed adopted file's second read would leave
  the entire Story 12.1 suite green while permitting a row whose checksum or
  length does not describe the stored document.
- Required remediation: add focused negative tests for same-length digest
  mismatch, the adopted two-read disagreement, and the database length CHECK.
  This is coverage-only; demonstrate the first two tests red against a
  deliberate uncommitted guard mutation, then restore the correct code.
- Red-first evidence: pending.
