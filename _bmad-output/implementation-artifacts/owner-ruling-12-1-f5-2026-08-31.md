# Owner ruling — Story 12.1 finding F5, and the rerun's delete

**Ruling, 2026-08-31: land story 12.1 as it stands. Record F5 as a known
latent defect scoped to the approval workflow. Deleting the previous artifact
set on a rerun is correct for current capabilities.**

## What F5 actually is

The review found a conflict between two frozen contracts:

- Story 4.1: a rerun **skips** any moment already carrying an `approved` or
  `published` artifact, leaving that whole set — drafts included — exactly as
  the human last saw it.
- Story 12.1: the one `(meeting_id, kind)` document row is **replaced** on
  every rerun.

So an approved artifact can survive while the only readable document for its
kind is a later reply that did not produce it. The provenance purpose of
retaining the document is defeated for the highest-value rows.

## Why it does not block the story

**The conflict requires an approved artifact, and there are none.** Measured on
the corpus 2026-08-31: **772 artifacts, all in state `extracted`, zero
approved, zero published.** There is no approval workflow in use — the owner
confirmed it directly: *"There's not some rigorous approval process right now
for artifacts. I think it would be good if there was, but it's simply not
happening today."*

With nothing approved, every rerun deletes its drafts and replaces the document
in the same pass, so artifacts and document stay consistent by construction.
F5 becomes reachable the day the first artifact is approved, not before.

**Do not build the fix now.** When the approval workflow is built, the fix is
versioned `extraction_source` rows plus an immutable artifact-to-source
reference — the option that preserves provenance without breaking story 4.1's
guarantee. That belongs to the approval story, which will already be changing
this area, and not to a story whose job is to stop throwing the document away.

## The rerun's delete, ruled separately

The owner's habit is to re-extract and then merge the two artifact sets by
hand: *"if I have an action items list from a previous extraction and then I
extract action items again, I'll usually ask the LLM to merge the two artifacts
together."* The system does not support that — `_DELETE_DRAFTS` removes every
`extracted` artifact for the meeting before re-proposing, so the previous set is
gone and there is nothing left to merge against.

**Ruled: that is fine for current capabilities.** Merging happens outside the
system today. Do not add superseded-artifact retention, and do not treat the
delete as a defect.
