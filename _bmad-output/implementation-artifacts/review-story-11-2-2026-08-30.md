## Findings

### 1. Incomplete or incoherent worktree metadata can silently target another stack

- **Location:** `infra/Makefile:224-227`; `infra/worktree_stack.py:63-66,196-207,275-303`; `server/tests/conftest.py:206-244`
- **Severity:** high
- **Sources:** `blind-hunter+edge-case-hunter+verification-gap+acceptance-auditor`
- **Finding:** The linked-worktree guards accept any readable `.env.worktree`, while the provisioner requires only the stack name and seven ports and does not validate ownership, port coherence, the two destructive test-twin URLs, or foreign keys.
- **Evidence:** `check-env` and `linked_worktree_without_stack()` check only file readability/existence; `REQUIRED_KEYS` omits `MM_TEST_NEO4J_URI` and `MM_TEST_MEILI_URL`; and an existing file bypasses allocation after `check_env_file()` without checking that `MM_STACK_NAME` matches the requested slug. A direct diagnostic removed both twin URL lines from `render_env(...)`; `check_env_file()` still accepted the resulting eight keys. `twin_endpoints()` then defaults missing URLs to the main checkout's twins at 7688/7701, and `projection_stores` calls `drop_all()` there. A shorter readable file can also leave the worker on the main dev ports. The current write uses non-atomic `Path.write_text()`, so interruption can create exactly such a partial file; `test_linked_worktree_without_stack_file_is_refused_by_name` explicitly treats a name-only file as sufficient.
- **Suggested direction:** Make every linked-worktree entry point fail closed on one exact, coherent generated-file schema: expected project name for the checkout, all seven valid distinct ports, both twin URLs derived from the declared test ports, and no foreign keys. Publish new files atomically or otherwise ensure an interrupted write cannot become accepted state.

### 2. The orphan pruner accepts invalid `meetingminer-*` project names as owned worktree stacks

- **Location:** `infra/worktree_stack.py:359-360,393-420,424-476`
- **Severity:** high
- **Sources:** `blind-hunter+edge-case-hunter+acceptance-auditor`
- **Finding:** `_is_worktree_project()` checks only the `meetingminer-` prefix, so projects whose suffix cannot be a valid story slug enter the destructive `down -v` path.
- **Evidence:** The provisioner accepts only `[a-z0-9][a-z0-9_-]*`, but the pruner accepts `meetingminer-Foo`, `meetingminer-.backup`, and even `meetingminer-`. A direct call to `worktree_stacks()` classified `meetingminer-Foo` with a missing working directory as a removable, known stack (`unknown=False`, no present owner). `prune()` would therefore issue `docker compose -p meetingminer-Foo down -v --remove-orphans`, contrary to the contract that another project is never removed.
- **Suggested direction:** Require the project suffix to satisfy the exact provisioner slug rule before a project can enter pruning, and add destructive-path regression coverage for malformed-prefix foreign projects.

### 3. A container label bypasses the pruner's foreign-volume safety check

- **Location:** `infra/worktree_stack.py:379-420`
- **Severity:** high
- **Sources:** `blind-hunter+edge-case-hunter`
- **Finding:** Once a candidate has any container working-directory label, `worktree_stacks()` skips volume recognition entirely, so a missing directory makes `prune()` delete even explicitly unrecognized volumes.
- **Evidence:** Lines 405-413 return the stack as soon as `stack.owners` is non-empty; the expected-volume check at lines 414-419 runs only for volumes-only projects. A direct diagnostic supplied a missing `.../infra` label plus `meetingminer-probe_foreign-data`; the stack was classified `unknown=False` with no present owner. The module contract says any project whose volumes are not recognized is reported and left alone, but `prune()` would pass `-v` and delete that volume.
- **Suggested direction:** Validate every discovered candidate's labeled volumes before destructive teardown, regardless of whether containers supplied an owner path, and test the mixed container-plus-foreign-volume case.

### 4. Failure recovery for a pre-11.2 worktree either cannot run or starts the main stack

- **Location:** `infra/Makefile:298-312`; `AGENTS.md:49-58`
- **Severity:** high
- **Sources:** `blind-hunter`
- **Finding:** `make worktree BASE=<pre-11.2-ref>` correctly performs the initial startup through the invoking Makefile, but both printed recovery commands switch execution into the old checkout and lose that safety mechanism.
- **Evidence:** On provisioning failure, line 300 directs the user to `cd <old-worktree> && make worktree-provision`, although that target and `worktree_stack.py` do not exist in the old ref. On Compose failure, line 312 directs `cd <old-worktree> && make infra-up`; the old Makefile does not read `.env.worktree` and starts the fixed `meetingminer` project. The existing old-ref test proves the checked-out Makefile may be pre-11.2 but exercises only successful initial startup; the supplied final report explicitly lists the provision-failure branch as untested.
- **Suggested direction:** Keep every retry for an old-ref worktree routed through a post-11.2 invoking Makefile and compose file with the new worktree's env/project-directory overrides; the documented command must work for both provisioning and startup failures without ever entering the old stack logic.

### 5. Docker-down creation can revive stale volumes when the documented retry runs

- **Location:** `infra/Makefile:289-312`; `server/tests/test_makefile_procs.py:1596-1612`
- **Severity:** medium
- **Sources:** `blind-hunter`
- **Finding:** `make worktree` skips the stale-project sweep while Docker is unavailable, then its retry starts the same project name without sweeping it, so a reused slug can attach to abandoned volumes.
- **Evidence:** Line 292 conditionally omits `prune --project` when `docker info` fails, but still adds the checkout and writes `.env.worktree`. The only recovery instruction is direct `make infra-up`, which has no stale-stack check. The Docker-down test asserts this exact command but provides no stale project. When Docker returns, Compose reuses volumes named for `meetingminer-<slug>`, defeating the stated guarantee that reuse first removes a hand-deleted worktree's old stack.
- **Suggested direction:** Make the retry path perform the same stale-owner check and teardown as normal creation before starting Compose, while still refusing a stack with a live owner.

### 6. Worktree cleanup can return success after stack discovery or teardown failed

- **Location:** `infra/Makefile:272-281,354-375`
- **Severity:** medium
- **Sources:** `blind-hunter+edge-case-hunter`
- **Finding:** `stack_down` treats failed Docker inventory calls as an absent stack, and `worktree-prune` can mask a failed `docker compose down -v` with the following branch-deletion command.
- **Evidence:** The `docker ps` and `docker volume ls` substitutions discard stderr and their status; if both fail after `docker info` succeeds, the macro prints “already gone” and returns success. If Compose itself fails, line 369 is nonzero, but line 371 ends in `|| true`, restoring a successful loop status. The checkout and branch can therefore be removed while the target reports success and leaves the stack/volumes orphaned. Existing Make-level tests cover only successful teardown and dirty-checkout refusal.
- **Suggested direction:** Treat inventory failure as a named nonzero result, propagate every teardown failure through `worktree-remove`/`worktree-prune`, and add fakes that fail inventory and `down -v` separately.

### 7. Pruning races worktree creation after taking its ownership snapshot

- **Location:** `infra/worktree_stack.py:275-303,424-476`; `infra/Makefile:284-312,587-592`
- **Severity:** medium
- **Sources:** `acceptance-auditor`
- **Finding:** The provision lock excludes only concurrent allocation; `prune()` neither takes it nor rechecks ownership immediately before teardown, leaving a stale-stack snapshot able to delete a newly recreated live stack of the same slug.
- **Evidence:** `prune()` inventories Docker and resolves `present_owner` once at lines 441-451, then later runs `down -v`. A concurrent `make worktree STORY=x` can sweep the same stale project, create the checkout, provision it under `.provision.lock`, and start its replacement after the other pruner's snapshot but before that pruner's teardown. The stale pruner then removes the replacement and its volumes even though the owner directory now exists.
- **Suggested direction:** Serialize destructive stack pruning with creation and/or re-resolve authoritative ownership immediately before each `down -v`; add a coordinated concurrency regression covering stale-project reuse versus `test-db-prune`.

### 8. The provisioning lock's exclusion behavior is unverified

- **Location:** `infra/worktree_stack.py:275-303`; `server/tests/test_worktree_stack.py:116-127,171-182`
- **Severity:** low
- **Sources:** `verification-gap`
- **Finding:** Tests assert only that `.provision.lock` exists; none proves that two simultaneous provisions hashing to the same base wait through allocation and publication and receive disjoint ports.
- **Evidence:** Sibling collision tests are sequential, and `test_provision_writes_once_and_keeps_a_complete_existing_file` checks only `lock.exists()`. Removing the `flock` acquire/release leaves the checked tests green even though two concurrent creators can both inspect the root before either publishes `.env.worktree` and persist the same seven ports.
- **Suggested direction:** Add a coordinated multi-process test that forces two slugs to the same starting base, overlaps their allocation windows, and proves the second observes the first file and advances to a disjoint base.

### 9. The projection lock-key validator accepts a trailing newline

- **Location:** `server/meetingminer/projections/locks.py:58-76`; `server/tests/test_projections_locks.py:81-90`
- **Severity:** low
- **Sources:** `acceptance-auditor`
- **Finding:** `_KEY_RE.match()` with a `$` anchor accepts a final newline even though the documented contract allows only `[A-Za-z0-9._-]{1,64}`.
- **Evidence:** A direct Python diagnostic confirmed the compiled pattern matches `"b14-key\n"`; the invalid-value parameterization omits newline cases. The accepted value becomes part of the lock and holder filenames.
- **Suggested direction:** Validate the entire string with `fullmatch()` (or an equivalent strict end anchor) and add trailing-newline regression cases.

### 10. Three required documents omit the concrete Docker VM bound

- **Location:** `README.md:351-355`; `project-context.md:102-108`; `docs/glossary.md:306-309`
- **Severity:** low
- **Sources:** `acceptance-auditor`
- **Finding:** README, project-context, and the glossary point readers to AGENTS.md instead of each stating the measured OrbStack VM bound required by the documentation acceptance criterion.
- **Evidence:** The frozen AC requires AGENTS.md, README, project-context, and the glossary each to state the per-worktree stack, measured memory, OrbStack VM bound, and fixed API/web ports. AGENTS.md states 23.5 GiB and the 128 GB host at lines 156-167; the other three say only that “AGENTS.md carries the measurement and the Docker VM bound.”
- **Suggested direction:** Put the concrete OrbStack bound and its operational implication directly in each required document, while keeping AGENTS.md as the detailed measurement source.
